## 메모

- run 11(100명)이 run 12(400명)보다 느렸다 — 앱 재기동 뒤 첫 본 측정이라 JVM 워밍업 영향으로 본다. 2·3회차에서는 측정 전 워밍업 회차를 따로 두고 버린다.
- run 14는 설계 실수로 동시 시작 + 동시 종료가 됐다. 시작은 통과(왕복 37ms → 941ms), **400명 동시 종료는 68%가 실패**(30초 무응답 271, INTERNAL_SERVER_ERROR 95). 종료 한 건이 트랜잭션 안에서 S3 동기 업로드까지 하므로 커넥션 풀(10) 고갈로 추정 — 로그·커넥션 지표로 확인 필요. 이후 start-storm은 종료를 2분에 퍼뜨린다.
- run 14 서버 지표(Grafana, 동시 종료 시점 19:08:40 KST 전후):
  - 커넥션 active 10/10, pending 최대 24. 획득 대기·사용 시간 최댓값 약 30초(획득 제한 30초에 걸림)
  - CPU 프로세스 74%·서버 97%까지 치솟음. 힙은 최대 약 300MiB/460MiB, GC 정지 최대 3ms — 메모리·GC는 원인이 아니다
  - 약 35초 동안 모든 지표가 비었다 — 앱이 Prometheus 수집 요청에도 응답하지 못했다
  - 같은 구간 Redis 상태 접근 실패 0건. p50 1~2ms → 동시 종료 때 최대 67ms, p99는 동시 배치 몰림마다 100~330ms
  - 결론: 원인은 Redis가 아니라 종료 트랜잭션이 커넥션을 쥔 채 S3 업로드·날씨 조회·트랙 분석을 하는 구조. 같은 방 행 잠금을 기다리는 트랜잭션도 커넥션을 쥐고 기다린다
- run 17(동시 시작, 종료 분산)은 전원 성공. 같은 400명인 run 12(시작 60초 분산)와 비교하면:
  - 시작 왕복 med 49ms → **1,090ms**, p95 81ms → 2,140ms. 핸드셰이크도 med 7ms → 463ms
  - 배치 왕복 med는 같고(6~7ms) p95가 23ms → **377ms** — 같은 초에 시작해 10초마다 400개 배치가 한꺼번에 들어오는 몰림이 꼬리 지연을 만든다
  - 종료 왕복은 더 빠르다(med 82ms) — 러닝이 5분이라 트랙이 짧고, 종료가 2분에 퍼졌다
- run 15(400명이 1분 안에 종료, 초당 약 7건)는 전원 성공, 종료 med 188ms·p95 326ms. run 14(400명이 같은 순간)는 68% 실패 — 같은 인원이라도 **몰리는 밀도**가 갈랐다. Redis 프로필의 안전 구간은 "1분에 400건"과 "한 순간 400건" 사이에 있다.
- run 16(Redis 장애): 11:20:04 UTC에 `systemctl kill -s KILL redis-server` → systemd가 0.1초 뒤 재시작(`Restart=always`), 마지막 RDB 스냅샷(약 1분 주기, AOF 꺼짐)을 읽어 복구.
  - **사용자 체감은 거의 없다** — 에러 0, 끊김 0, 종료 400/400. 배치 왕복 최대만 607ms로 튐. 앱 로그의 Redis 연결 오류 3건, 재시작 순간 상태 접근 지연 WARN이 몰림
  - **데이터는 조용히 잃었다** — 종료 시 좌표 공백(`gapEdgeCount ≥ 1`)이 있는 러너가 run 12는 0/400, **run 16은 400/400**. 스냅샷 이후의 좌표가 모든 러너에서 사라졌다
  - 기록 거리는 run 12와 똑같았다(평균 1,704m) — 가짜 트랙이 직선이라 공백을 직선으로 이어도 거리가 같기 때문이다. 곡선을 달리는 실제 사용자는 같은 공백이 거리 손실로 나타난다(테스트 설계의 한계)
  - 콤보는 14,932 → 14,774(약 1% 감소) — 콤보 상태 일부 손실로 보이나 오차 범위와 겹친다
  - 결론: EC2 직접 운영 Redis의 위험은 "멈춤"보다 "AOF 없이 1분치 상태가 조용히 사라지는 것"이다. 에러가 나지 않아 운영 중에는 알아차리기 어렵다
- 1,000명에서도 배치 왕복이 400명과 거의 같다(med 7ms, p95 27ms). 러너 1,000명 = 초당 배치 약 100건이라 처리량으로는 아직 여유 구간이다. 한계는 이보다 위에 있다.
