## 실행 규칙

`초안 (D-57 정함, 숫자는 동결 전까지 초안)` — 반증할 수 있게 짠다(D-25). 비교군 A · A′ · B0 · B2에 견준다(D-57).

**비교군**
1. **같은 비용 · 자원** — A · A′ · B0는 t3.small 2대(4 vCPU · 4 GiB)를 쓰고 DB 연결은 합해서 20(10 + 10)이다. A′R2는 앱 2대에 Redis 2대다. B2는 앱 2대(메인 1 · 세션 1)이고, DB 연결 합은 A′와 같다. 대조군(비용이 다른 A-4x, SC11의 J1–J4 · 한계 측정 장비)은 순위에 넣지 않는다. A′-unlimited는 버렸다(D-64).
2. **같은 빌드** — 코드가 같은 비교군(A′ · A′c · A′R2 · A′-burst · B0 · B0-main · B0-session)은 같은 이미지 digest를 쓰고, 역할과 변형은 환경 변수로만 가른다. JVM 옵션은 `JAVA_TOOL_OPTIONS`로 똑같이 준다. 다르게 주는 것은 SC11의 J1–J4와 SC10의 A′+VT뿐이다. 코드가 다른 A′+JSONB와, A vs A′에서 수정을 하나씩 넣거나 가장 큰 두 수정을 뺀 이미지(verification 「판정과 결과」)는 따로 빌드하고 digest를 회차에 적는다. 비교군 사이 환경 파일 차이는 회차마다 보관한다.
3. **분리 비교군은 A′와만 견준다** — B0 · B2를 A에 견주어 근거를 지지하지 않는다. A와 A′의 비교는 '모놀리스에서 고침' 장에만 쓴다.

**부하**
4. **같은 부하** — L30 · L60 · L100은 SC0에서 잰 REST_CAP(A)의 0.3 · 0.6 · 1.0배다. 하네스 프로필에 절대값(rps)으로 얼리고, 모든 비교군에 같은 값을 준다. 다른 비교군의 REST_CAP는 보고만 한다. REST 혼합 비중은 verification 「보조 시나리오 SC0 · SC8–SC14」의 값을 쓴다.
5. **같은 러너** — run_id마다 러너 수 · 시드 · 거리 분포 · 페이스 시드를 비교군 사이에 똑같이 둔다.
6. **HTTP는 열린 모델** — `constant-arrival-rate` · `ramping-arrival-rate`만 쓴다.
7. **WS는 닫힌 모델이고 VU 하나가 방 하나다** — VU 하나가 소켓 4개를 연다. 소켓 핸들러 안의 REST는 `http.asyncRequest`로 보낸다. 한 방의 소켓을 여러 k6 호스트에 나누지 않는다.
8. **시간 제한이 결과를 자르지 않게 한다** — REST는 10초다. 끝내기는 ack를 15초 기다린 뒤 재시도하고, 성공은 60초까지 센다. 서버 쪽 ack 지연은 따로 적는다. A′의 Hikari `connectionTimeout`은 5초로 명시한다(F5). A는 운영 기본값(풀 10, 30초)을 쓴다. 클라이언트 시간 제한을 서버 시간 제한과 같은 값으로 두지 않는다.
9. **날씨 스텁** — 기본은 운영 `weather.timeout`(2초)과 같은 `WEATHER_STUB_DELAY_MS=2000` 고정이다. SC8만 실제형 분포를 쓴다: 1,000 ± 300 ms, 5%는 2,500 ms라 시간 초과 경로를 탄다. SC3의 C5는 이와 따로 2초 뒤 멈춘다.
10. **실제 의존성** — 같은 리전의 실제 S3 버킷과 ALB의 TLS를 쓴다. ALB · 대상 그룹 · ASG 설정은 운영 값을 베껴 회차에 적는다([platform.md](../../docs/msa/platform.md) 「확인할 운영 값」). 인스턴스 수만 운영(1대)과 달리 둘로 둔다(verification 「비교군」 A). 앱 재접속 정책은 [runtime.md](../../docs/msa/running-session-server/runtime.md)의 값을 쓴다. 장애 시나리오(SC3 · SC4)에서는 장애를 넣지 않는 비교군과 구간에도 toxiproxy를 둔다.

**반복 · 순서**
11. **남는 회차 n ≥ 3** — 비교군 × 시나리오마다 남기는 회차가 3개 이상이어야 한다.
12. **워밍업 회차는 버린다** — 앱을 띄우거나 다시 띄운 뒤에는 `load-400` 10분을 한 번 돌리고 버린다. SC1 · SC2의 새 인스턴스는 운영과 같이 데우지 않은 채로 둔다.
13. **순서는 무작위 블록으로** — 블록마다 모든 비교군을 한 번씩 돌리고, 블록 안 순서는 무작위로 정한다(시드는 RESULTS에 적는다). 한 비교군을 몰아서 돌리지 않는다. 회차 사이에는 3분 쉰다.
14. **상태 초기화** — 회차마다 Redis `FLUSHALL` 뒤 `BGREWRITEAOF`를 하고, DB 정리와 `VACUUM ANALYZE`(또는 블록마다 스냅샷 복원)를 한다. run_id를 새로 쓰고 S3 prefix를 정리한다. B2는 러닝 DB까지 초기화한다. 러너 사용자와 보기 사용자는 겹치지 않는다. 절차는 RUNBOOK 「3. 상태 초기화」.

**측정 환경**
15. **발생기 · 시계** — k6는 버스트 없는 c 계열 호스트에서 CPU ≤ 70%로 돌린다. 모든 호스트의 chrony offset은 ≤ 10 ms다.
16. **CPU 크레딧** — 시작할 때 모든 t3의 `CPUCreditBalance`가 ≥ 150이어야 한다. 아니면 모든 비교군을 Unlimited로 돌린다. 쓴 잉여 크레딧을 적는다.
17. **k6 고정** — k6 이미지는 digest로 고정한다.
18. **표본 수** — 창마다 p95는 표본 ≥ 400, p99는 ≥ 2,000이 필요하다. 모자라면 인증된 REST 전체를 합친 값을 쓴다. 기울기는 95% 신뢰구간과 함께 적는다.

**무결성 · 안전**
19. **무결성 검사** — [README.md](README.md) 「무결성 검사」를 통과한 회차만 성능 판정에 쓴다. 통과 조건: 유효 러너마다 기록 1건 · 구간 수 = floor(거리 / 10 m)(`running-finish.split-distance-meters`) · 방이 닫히고 `RUNNING`으로 남은 참가자 0 · S3 트랙에 보낸 sequence가 모두 있다 · ack_without_record 0(I1) · I2 · I3 어긋남 0 · B2는 러닝 DB와 메인 사본 사이에 빠진 기록 0(I5). 재신청을 재는 회차는 I6 · I7도 본다. 통과하지 못하면 기능 결함으로 RESULTS 「무결성」에 적는다.
20. **격리** — 부하 시험 호스트는 dev CI 배포 대상으로 쓰지 않는다. 공용 dev/test Kafka에 붙는 부하 시험 앱은 `KAFKA_CONSUMER_ENABLED=false`로 띄운다. 부하 시험 DB에는 지연 측정용 Debezium 커넥터 하나만 둔다. Kafka 장애(C3 · SC6 · R5)는 버리는 브로커에만 내고, 공용 dev/test 클러스터에는 내지 않는다. k6는 운영을 겨누지 않는다.
21. **개인정보 · 비밀값** — 가짜 사용자만 쓴다. 운영에서는 합계(백분위 · 개수 · 시간별 계열)만 가져온다. JWT 서명 값은 파일에서 읽고 출력하지 않는다. 시험 버킷의 원본 트랙은 캠페인이 끝나면 지운다.
22. **출처** — 회차마다 [RUNBOOK.md](RUNBOOK.md) 「6. 회차마다 남길 것 · 정리」의 목록을 RESULTS 「회차 색인」에 적는다.

## 판정 방식

`초안 (D-57)`

| 창 | 정의 | 쓰는 곳 |
|---|---|---|
| REST 단독 | 회차 시작 뒤 REST만 도는 5분 | 비율의 기준 |
| 배포 전 | 배포 시작 전 3분 | SC1 · SC2 · R1 · R7 |
| 배포 | 배포 시작부터, 마지막 새 인스턴스(파드)가 대상 그룹에서 healthy가 되고 2분 뒤까지 | SC1 · SC2 · R1 · R2 · R7 |
| 폭주 / 직전 | [T0, T0 + 30초] / [T0 − 5분, T0) — T0는 슬롯 시작 시각 | SC5 · SC8 |
| 장애 / 회복 | 장애를 넣은 때부터 풀 때까지(SC3 120초, SC4 정지 60초) / 그 뒤 5분 | SC3 · SC4 |
| 몰림 전 / 몰림 | 끝내기를 보내기 전 5분(상시 러너 + REST L60) / 끝내기를 보낸 때부터 마지막 ack까지(최대 60초) — 포화 회차는 두 배 단계마다 | SC9 |
| 급증 전 / 급증 / 포화 | REST L60과 러너가 함께 도는 첫 5분 / 5 × L60으로 2분 유지 / REST_CAP_db로 2분 유지 | SC10 |
| 1분 | 회차를 1분씩 자른 창 | SC8 |
| 종료 창 (운영) | 옛 인스턴스 종료 시각 ± 10분. 종료 시각은 ASG 활동 기록에서 읽고, 없으면 머지 + 10분 | `K-SC1-1` |

- **비율의 기준** — 비율(배)은 같은 회차의 REST 단독 창(SC1 · SC2는 배포 전 창, SC5는 직전 창, SC9는 몰림 전 창, SC10은 급증 전 창) 값으로 나눈다. 다른 회차나 다른 비교군의 값으로 나누지 않는다.
- **판정** — 남긴 회차 3개 모두에서 기준이 성립해야 판정한다. 결과가 섞이면 2회 더 돌리고 5회 중앙값으로 판정한다. 보고는 중앙값 [최소–최대]와 n으로 한다. 가장 좋은 회차만 내지 않는다.
- **고친 뒤에 견준다** — 지지는 A′가 기준을 넘지 못하고 B0나 B2가 남긴 회차 모두에서 넘을 때만 적는다. A′가 넘으면 '모놀리스에서 고침'으로 기각한다.
- **AG6** — 근거마다 본다. B0(SC4에서는 A′R2)가 그 근거의 지지 쪽 기준을 모든 회차에서 넘으면, 그 근거 몫의 AG6를 지지로 적는다.
- **판정 낱말** — `지지` · `기각` · `판정 못 함`(유효 회차 3개를 모으지 못했다) · `분리 뒤에만`(기준에 B2가 필요한데 B2가 아직 없다) · `안 돌림`. 반대 근거(AG)가 지지라는 것은 그 반대 근거가 맞았다는 뜻이다. 관문(SC0)과 구성 확인은 `통과` · `실패`로 적는다.
- **무효 회차** — dropped_iterations > 0 · k6 CPU > 70% · chrony offset > 10 ms · early_start_reject > 1% · 크레딧 규칙 위반 · 다른 장애가 겹침 · AOF 다시 쓰기나 bgsave가 판정 창에 겹침 · 시나리오의 유효 조건 위반이면 회차를 버린다. 무결성 검사에 실패한 회차는 성능 판정에서만 뺀다. 버린 회차는 n에 세지 않고, RESULTS 「회차 색인」에 이유와 함께 남긴다.
- **빗나간 예측** — 결과가 「비교군별 예측」과 다르면 RESULTS 「판정 상세」의 빗나감 칸에 남긴다. 기각된 근거도 표에서 지우지 않는다.
- **적는 곳** — 회차 숫자는 RESULTS에, 근거마다 판정 한 줄은 verification 「판정과 결과」에, 판정 낱말은 rationale 「근거 순위」에 적는다. 셋은 같은 PR에서 고친다. 결과는 세 장으로 나눈다: 지금 (A) / 모놀리스에서 고침 (A vs A′) / 분리 (A′ vs B0 · B2).
