# 명세·구조 정합성 점검

구조 위반은 스크립트와 수동 확인으로 검사하고, 명세 불일치는 현재 문서와 구현을 직접 대조한다.

진단 단계에서는 명시적으로 요청된 테스트가 만드는 빌드 산출물을 제외하고, 저장소 내 파일을 추적 여부와 관계없이 생성·수정·삭제하지 않는다. 진단만 요청되면 차이·영향·판단 근거를 보고하고 종료한다. 진단과 수정이 함께 명시되면 진단 보고를 먼저 완성한 뒤 별도 구현 단계로 전환한다. 사용자가 수정 기준이나 바꿀 대상을 이미 제시한 항목만 곧바로 수정한다. 그 외 `docs/api-spec.md`·`docs/erd.md`·`docs/feature-spec.md`와 코드의 불일치, 또는 선택에 따라 공개 API·데이터 계약·업무 동작·권한이 달라지는 충돌은 어느 쪽을 기준으로 할지 사용자에게 확인한다.

## 0. 요청 유형과 범위

먼저 `CLAUDE.md`와 `docs/architecture.md`를 읽고 요청 유형을 구분한다.

- **구조 점검**: §1만 수행한다.
- **구현 정합성 점검**: 대상 기능의 §1·§2를 수행한다.
- **문서 간 정합성 점검**: 대상 문서·기능의 §3만 수행한다.
- **종합 점검·명세/아키텍처 관점의 PR 점검**: 변경 범위와 직접 의존 경로에 해당하는 §1~§3을 수행한다.
- **전체 구현·누락·완성도 점검**: 명세에만 있는 REST 엔드포인트와 WebSocket 메시지도 포함한다.

사용자가 범위를 지정하면 진입점부터 `port/in`, Handler, 도메인, `port/out`, 어댑터·엔티티까지 직접 호출·의존하는 경로를 포함한다. 인증·예외·직렬화처럼 결과에 직접 영향을 주는 공통 구현도 포함한다. 범위 밖 발견 사항은 보고하지 않는다.

범위 없는 구현 정합성 점검은 구현된 진입점 전체, 범위 없는 구조 점검은 main Java 소스 전체를 대상으로 한다. PR 기준 diff가 제공되지 않았다면 현재 staged·unstaged 변경만 확인하고 그 한계를 보고한다.

다음 명령은 진입점 **후보** 검색용이다. 각 파일을 열어 클래스·메서드 매핑을 조합하고 실제 경로와 WebSocket destination을 확정한다.

```bash
rg -n '@(RestController|Controller|RequestMapping|GetMapping|PostMapping|PutMapping|PatchMapping|DeleteMapping|MessageMapping|SubscribeMapping)\b|WebSocketHandler' running-service/src/main/java -g '*.java'
```

판정 기준은 항목별 현재 문서다. 레이어·트랜잭션·포트는 `docs/architecture.md`, API 표면은 `docs/api-convention.md`와 `docs/api-spec.md`, 저장 구조·enum은 `docs/erd.md`, 업무 동작은 `docs/feature-spec.md`를 따른다. 같은 영역의 현재 문서가 충돌하면 임의로 우선순위를 만들지 않고 조사 필요로 둔다.

## 1. 구조 검사

저장소 루트에서 실행한다. 두 번째 인자는 소스 루트 기준의 Java 파일 또는 디렉터리 하나다. 전체 검사는 두 번째 인자를 생략하며, 여러 범위는 각각 실행한 뒤 결과를 중복 제거한다.

```bash
python3 .claude/skills/spec-check/scripts/check_conventions.py .
python3 .claude/skills/spec-check/scripts/check_conventions.py . application/user
```

위반·의심 발견은 종료 코드 `0`, 잘못된 인자·루트·범위는 종료 코드 `2`다. 종료 코드와 함께 세 결과 섹션 및 마지막 건수 요약이 모두 있는지 확인한다. 오류 문구, traceback 또는 stderr가 있으면 실행 실패로 처리한다.

실패하면 루트와 범위를 바로잡아 한 번 재실행한다. 그래도 실행할 수 없으면 이 절의 레이어 의존 방향·application 구성·트랜잭션·포트·아웃바운드 네이밍을 수동 검사한다. 대체하지 못한 항목과 이유는 조사 필요로 보고한다. §2는 구조 검사의 대체가 아니다.

스크립트는 레이어 의존 방향, application 구성·트랜잭션, 아웃바운드 구현체 네이밍, 에러 등록 후보, 미사용 예외, 포트 규칙, DTO 단위 접미사를 검사한다. 출력 분류는 잠정 결과이며 현재 코드와 기준 문서를 직접 확인한 뒤 최종 재분류한다.

스크립트는 여러 점검 축을 한 번에 출력하지만 최종 보고에는 §0에서 선택한 축만 포함한다. 구조 점검만 요청됐으면 레이어·application·포트·아웃바운드 항목만 보고하고 에러 노출·DTO 단위 결과는 미적용으로 둔다.

범위 지정 실행의 에러 코드 결과는 단독으로 최종 판정하지 않는다. 실제 throw 지점 → application 예외 → application `ErrorCode` → `toStatus()` → API 공개 계약 → `EXPOSED_CODES` 또는 마스킹 경로를 추적한다. domain의 동명 `ErrorCode`는 제외하고, 좁은 범위 결과만으로 "등록 코드 없음"이나 "모두 정상"이라고 보고하지 않는다.

스크립트가 확정하지 못하는 다음 항목을 직접 확인한다.

- 포트와 어댑터의 분리·통합이 사용 유스케이스와 변경 이유에 맞는지, Handler가 필요한 포트만 주입받는지 확인한다. 같은 애그리거트·저장 기술의 여러 포트를 한 어댑터가 함께 구현하는 것은 선택 사항이며, 분리 자체를 위반으로 보지 않는다.
- 포트 구현체의 `*Adapter`·`*Client`·`*Router` 접미사가 실제 역할과 일치하는지 확인한다. 허용 접미사 중 하나라는 이유만으로 통과시키지 않는다.
- 어댑터가 애그리거트를 반쪽만 복원해 도메인 메서드가 죽은 코드가 됐는지 확인한다.
- 같은 일을 하는 포트가 이름만 다르게 중복됐는지 확인한다.

## 2. 명세와 구현 대조

각 엔드포인트 상세뿐 아니라 `docs/api-spec.md` §0의 적용 가능한 공통 규칙도 먼저 대조한다.

| 볼 것 | 구현 |
|---|---|
| 유효 경로·HTTP 메서드 | `server.servlet.context-path` + 클래스·메서드의 `@*Mapping`을 조합한 실제 경로 |
| 인증·인가 | 인증 필터·Security 설정 + 현재 사용자 주입 + 소유자·역할·참가자 권한 검사 |
| 헤더·경로·쿼리 파라미터 | `@RequestHeader`/`@PathVariable`/`@RequestParam` + 타입·필수 여부·기본값·최댓값·클램프 동작 |
| 요청 필드·검증 | Request DTO·Jackson 매핑 + `@Valid`/`@Validated` 적용 + 모든 Bean Validation 제약의 값·메시지 |
| 검증 메시지 | 각 제약의 `message`와 다중 실패 시 응답 조합 방식까지 실제 400 응답과 대조 |
| 응답 필드·타입 | Response DTO·매퍼·Jackson 직렬화 설정과 실제 JSON 형태 |
| 성공 상태 코드 | `ResponseEntity.ok/status/noContent`·`@ResponseStatus`·프레임워크 기본 상태를 포함한 실제 응답 |
| 에러 코드·상태·노출 | 실제 throw 지점 → 예외 변환기 → `toStatus()` → API 공개 계약 → `EXPOSED_CODES` 또는 마스킹 경로 |
| 멱등성·업무 동작 | Handler·도메인·포트 호출 + 중복 호출 결과·상태 변경·트랜잭션 |
| 시각·ID·단위·enum | DTO·매핑·도메인 타입과 `docs/api-spec.md` §0·`docs/api-convention.md`·`docs/erd.md` §6 |

JPA 엔티티는 `docs/erd.md` §0과 해당 표의 컬럼명·타입·nullable·PK·UNIQUE·FK/논리 참조·삭제 정책·감사 컬럼·소프트 삭제·단위·enum을 대조한다.

진단만 요청된 경우 빌드·테스트는 기본 완료 조건이 아니다. 사용자가 런타임 검증까지 요청했거나 별도 구현 단계에서 파일을 수정한 경우 `CLAUDE.md`에 적힌 가장 작은 관련 테스트·빌드·검증을 실행한다. 적용 가능한 검증이 없으면 이유를 밝힌다. `.env`는 존재 여부만 확인하고 내용을 읽거나 출력하지 않는다. 실행 실패는 명령·종료 코드·핵심 오류·미확인 항목을 보고하며, 의존성 설치·설정 변경·테스트 약화로 우회하지 않는다. 실패하거나 실행하지 못한 검증이 남으면 수정 완료가 아니라 부분 완료로 보고한다.

## 3. 문서 간 대조

§0에서 정한 범위에 걸리는 절만 대조한다.

- `docs/api-spec.md`의 공통·상세 규칙 ↔ `docs/api-convention.md`
- `docs/api-spec.md`의 동작·권한·1차 범위 ↔ `docs/feature-spec.md`의 해당 화면 절
- `docs/erd.md`의 저장 구조·enum·FK 정책 ↔ `docs/feature-spec.md`의 도메인 제약

## 4. 보고 전 — 현재 작업 상태와 이력 확인

먼저 `git status --short`로 기존 변경을 기록한다. 기존 변경을 되돌리거나 stash·checkout하지 않는다. 필요한 경우 직접 관련된 경로만 확인한다.

```bash
git diff -- <직접 관련된 경로>
git diff --cached -- <직접 관련된 경로>
git log --oneline -S "<코드 식별자>" -- <직접 관련된 경로>
git show --format=fuller <해시> -- <직접 관련된 경로>
```

Git 이력은 변경 배경을 파악하는 참고 자료이며 현재 규칙을 승인하거나 덮어쓰는 근거가 아니다. 현재 문서에 정확히 명시된 예외나 사용자가 확정한 기준만 예외 근거로 삼는다. 이력이 의도적 변경을 보여도 현재 문서와 충돌하면 조사 필요로 보고한다.

`.env`·키·토큰·자격 증명 파일은 열거나 출력하지 않는다. diff나 이력에서 민감정보로 보이는 값은 보고에 옮기지 말고 `[MASKED]`로 표시한다.

## 5. 보고 형식

- 결과를 **확정 위반 / 조사 필요 / 휴리스틱 의심**으로 나누고, 각 항목을 `항목 | 기준 | 대상 | 영향·판단` 형식으로 작성한다. 파일·줄 등 확인 가능한 근거를 붙인다.
  - **확정 위반**: 불일치 또는 명시적 규칙 위반의 존재가 확인됐다. 초안 문서 때문에 수정 방향이 정해지지 않았다면 `불일치 확정·수정 방향 미정`이라고 적는다.
  - **조사 필요**: 기준 문서가 충돌하거나 실행 실패·근거 부족으로 판정할 수 없다.
  - **휴리스틱 의심**: 명시적 금지는 없지만 구조적 냄새가 있어 수동 판단이 필요하다.
- 현재 문서에 정확히 명시된 기존 리팩터링 예외는 별도 **활성 임시 예외**, 수동 확인으로 오탐임이 증명된 항목은 **조치 불필요** 절에 둔다. 임시 예외의 신규 확장은 확정 위반이다.
- 각 분류 안에서는 공개 계약·런타임 동작에 미치는 영향이 큰 것부터 적는다.
- 실행 실패·미실행 항목은 명령·종료 코드·핵심 오류·미확인 범위를 적는다.
- 문제가 없더라도 점검 범위와 통과한 검사 항목을 적는다. 스크립트의 "위반 없음" 문구는 그대로 옮기지 않는다.

## 6. 마무리

§0에서 선택한 점검 축과 범위의 모든 필수 항목을 통과·발견·미적용·미확인 중 하나로 기록하고 §5 형식으로 보고해야 완료다. 미확인 항목이 남으면 전체 통과가 아니라 부분 점검으로 명시한다. 수정 단계까지 요청됐다면 변경 후 최소 관련 검증 결과와 잔여 미확인 항목까지 보고해야 완료다.
