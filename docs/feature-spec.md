# Runiverse 기능 명세서

## 1. 화면별 기능

> 화면 순서는 사용자 흐름 기준: 인증·온보딩 → 홈·매칭 → 러닝 → 기록 → 피드 → 프로필·설정 → 공통.

> **`[MVP 제외]` 표기**: 지금 만들지 않는 것. 본문은 그대로 두어 확장 시점에 재작성 없이 쓴다. 화면 단위로 제외되는 기능은 **탭과 라우트를 등록**하고 화면만 준비중으로 대체한다 — 탭을 숨기거나 비활성화하지 않는다.
>
> 마커가 없으면 만드는 것이다. 차수(1차·2차)는 적지 않는다 — 일정은 바뀌지만 "지금 만드나 마나"는 바뀌지 않는다.

### 인증·온보딩

**앱 진입(스플래시)**

- 앱을 열면 저장된 refreshToken으로 `POST /auth/refresh`를 시도하고, 성공하면 `GET /users/me`의 `isOnboarded`로 진입 화면을 가른다.

| refreshToken | `isOnboarded` | 진입 화면 |
|---|---|---|
| 없음·만료·무효 | — | 초기 페이지(로그인) |
| 유효 | `false` | 온보딩 |
| 유효 | `true` | 홈 |

- `POST /auth/refresh`는 토큰 두 개만 반환하고 `isOnboarded`를 담지 않는다 — 홈 렌더에 어차피 필요한 호출이라 `GET /users/me`로 판정한다.
- 서비스 소개 화면은 서버가 관여하지 않는다(완료 여부를 서버에 저장하지 않음) — 표시 정책은 클라이언트 문서에서 정한다.

**초기 페이지**

- 로그인 폼: 이메일·비밀번호 입력 필드 제공.
- 로그인 버튼: 입력한 이메일/비밀번호로 로그인 수행.
- 회원가입 버튼 → 회원가입 페이지로 이동.
- Google / Kakao 로그인 버튼: 소셜 계정으로 회원가입 또는 로그인. 네이버는 **[MVP 제외]**.
  - 인가 코드 + PKCE 방식: 앱이 provider 인증 후 인가 코드(`authorizationCode`)·`codeVerifier` 수령 → `POST /auth/oauth/google|kakao`로 서버 전달 → 서버가 provider와 코드↔토큰 교환(PKCE `codeVerifier` 검증) → 유저 정보 조회 → `provider_id`로 `oauth_users` 조회(없으면 생성=회원가입) → 자체 토큰 발급. 카카오는 SDK 앱 전환, 구글은 커스텀 탭으로 인가를 시작하고 커스텀 스킴으로 인가 코드를 돌려받는다 — 웹뷰는 provider가 차단한다.
  - 최초 가입 시 온보딩 화면을 거침 — `oauth_users` 생성 후 `user_onboardings` 입력 필요.
  - 카카오 이메일 미동의 시 403 가입 거부(`OAUTH_EMAIL_NOT_PROVIDED` — `users.email` NOT NULL 유지).

**약관 동의 화면**

- **회원가입 버튼을 누르면 가장 먼저 나온다.** 이용약관·개인정보처리방침을 링크로 제공하고 동의를 받은 뒤 이메일 인증으로 넘어간다.
- **소셜 가입에는 이 화면을 끼우지 않는다.** 소셜 버튼은 로그인과 가입을 겸하는데 신규 여부는 provider 응답을 받아봐야 알 수 있어, 앞에 약관을 띄우면 기존 사용자에게도 매번 뜬다. 대신 **초기 페이지의 소셜 버튼 아래에 동의 문구와 약관 링크를 둔다.**
- **서버는 동의 정보를 받지 않는다.** 별도 요청 필드도 저장 테이블도 두지 않고 가입 자체를 동의로 갈음한다 — 동의 시각 증빙은 `users.created_at`.

**회원가입 페이지**

- 회원가입 폼: 이메일, 인증번호, 비밀번호, 비밀번호 확인. 닉네임은 온보딩에서 받음 — `termsAgreed`는 signup 요청에 없음.
- 이메일 인증 3단계: 인증번호 발송 → 확인(`verificationTicket` 발급) → 티켓+비밀번호로 가입. 이메일은 티켓에서 꺼내 쓰므로 가입 요청에 담지 않음.
  - 이미 가입된 이메일은 발송 단계에서 409 차단 — 가입 여부 노출보다 UX를 택함.
  - 코드 5분·시도 5회, 재발송 쿨다운 30초·하루 10회, 티켓 30분 1회용.
- 회원가입 버튼: 입력 정보 검증 후 회원가입 수행. 가입 즉시 자동 로그인(토큰 발급) — 로그인 화면 거치지 않고 온보딩으로 이동.

**온보딩 화면**

- 온보딩 폼: 닉네임, 생년월일, 성별, 키, 몸무게, 평균 페이스 입력 후 제출. 약관 동의는 받지 않는다 — 가입 흐름 첫 화면에서 이미 받았다.
  - 닉네임 중복 체크(`NICKNAME_ALREADY_EXISTS`)는 온보딩 API의 에러 케이스.
  - 1회성 입력 — 닉네임만 `PATCH /users/{userId}/nickname`으로 수정 가능. 키·몸무게 수정은 **[MVP 제외]**. 평균 페이스는 수정 UI 없이 서버가 러닝 기록 기반 자동 갱신.

**하단 네비게이션 바**

- 홈 / 피드 / 기록 / 프로필 4개 버튼으로 각 화면 이동.
  - **피드 탭은 준비중 화면**으로 연결된다. 탭 자체는 노출하고 라우트도 등록해 확장 시 화면만 교체한다.

### 홈·매칭

**홈 화면**

- 날씨 정보: 현재 위치 기준 날씨 제공.
- 매칭 버튼: 설정된 조건으로 러닝 매칭 시작.
- 매칭 설정 버튼: 매칭 조건 설정 모달 오픈.
- 매칭 정보 입력 모달: 거리/시간 선택.
  - **자유 입력이 아니라 정해진 선택지에서 고른다** — 시작 시각은 **18:00~22:00 30분 간격**, 목표 거리는 **3·5·10km** 셋 중 하나.
    - 조건을 좁게 고정하는 이유는 매칭 성사율이다. 자유 입력이면 같은 조건에 두 명이 모일 확률이 급격히 떨어진다.
  - 시간 선택 박스에 **해당 슬롯의 대기 인원**을 함께 보여준다("19:00 · 3명 대기 중") — `GET /running-matches/slots`.
  - 페이스 조건은 입력받지 않는다 — 서버가 보관한 사용자 평균 페이스를 쓴다.
  - 모집 인원도 입력받지 않는다 — 서버가 2~4명 범위에서 자동 편성한다.
  - 활성 신청은 1개다 — 대기 중에 다시 신청할 수 없다.
    - **`INVITED`는 활성 신청에 넣지 않는다.** 수락도 하지 않은 초대에 묶여 랜덤 매칭을 못 걸면 내 의사와 무관하게 서비스가 막힌다. 초대는 여러 개를 동시에 받을 수 있고 받은 채로 랜덤 매칭도 신청할 수 있다. 활성 여부는 `deleted_at IS NULL AND status='JOINED'`인 행으로만 판정한다.
  - 매칭 방식은 랜덤 매칭과 친구 초대 두 가지. **친구 초대는 랜덤 매칭이 동작한 뒤에 붙인다** — 구현 순서상 후순위이지 범위 밖은 아니다.
  - `running_players` row 생성이 곧 매칭 요청 저장. "시간"은 목표 러닝 시간이 아니라 희망 시작 시각(예약 매칭) — `running_players.start_at`에 저장. "거리"는 `running_players.target_distance`(플레이어별 목표 거리)에 저장. 방 배정은 `running_room_sessions` row로 기록한다.
- 매칭 대기 화면: 매칭 진행 상태·남은 예상 시간·현재 참가자 확인.
  - **방 생성 시점**: **신청 즉시 1인 방**을 만들고 `status='MATCHING'`으로 둔다. 같은 조건에 다음 신청이 들어오면 그 방에 붙여 마감까지 최대 4명 모집한다. 즉 `MATCHING`은 "모집 중(마감 전)"인 구간이며, 인원 수는 조건에 들어가지 않는다.
    - 솔로 러닝도 개시 즉시 방이 생긴다 — 둘은 `running_rooms.type`(`MATCH`/`SOLO`)으로 갈린다. 매칭 후보 스캔은 `type='MATCH' AND status='MATCHING'`이라 솔로 방이 섞이지 않는다.
    - **"방 미배정" 상태는 없다.** 활성 신청이 있으면 방도 반드시 있고, 매칭 진행 단계는 배정 여부가 아니라 `running_rooms.status`로만 판정한다.
    - **왜 신청 시점에 만드는가** — 솔로는 원래부터 개시 즉시 방을 만든다. 매칭만 나중에 만들면 방 조회·상태 전이·WS 연결이 전부 두 갈래가 된다. 생성 시점을 맞추면 "방이 아직 없는 신청"이라는 상태가 사라져 홈 상태 판정·실패 처리·`runningRoomId` nullable 분기가 함께 없어진다.
      - 다만 **신청 row가 방을 직접 가리키지는 않는다.** 참가자가 재배정·병합으로 여러 방을 거칠 수 있어 배정은 `running_room_sessions`가 기록하고, 현재 방은 `is_connected`로 가린다.
      - 대가는 혼자 신청하고 아무도 오지 않은 방이 `CANCELLED`로 남는 것뿐이다. 조합(시각 9 × 거리 3)당 최대 하나라 양이 문제되지 않는다.
  - 확정 판정: 모집 마감 시각 `close_at`(`start_at - 설정값`)은 **방 생성 시 계산해 컬럼에 고정한다**. 그 시점 참가자가 2명 이상이면 `status='MATCHED'` 자동 확정 — 자리 수(`max_player_count`) 도달 여부와 무관하다. `max_player_count`는 상한이라 갱신하지 않고, 실제 인원은 `current_player_count`가 갖는다.
    - **마감 스케줄러는 `type='MATCH'`만 본다.** 솔로는 `close_at`이 null이라 애초에 대상이 아니고, 초대방은 "모집"이 아니라 지정 초대라 같은 마감 개념이 적용되지 않는다. 따라서 **초대방의 확정 시점은 친구 초대를 구현할 때 별도로 정해야 한다**(응답 기한을 둘지, `start_at` 도달로 처리할지).
  - 실패는 마감 시점 하나로 판정한다. **`close_at`에 참가자가 2명 미만이면 `status='CANCELLED'`** — 방은 신청 즉시 생기므로 "취소할 방이 없는" 경우가 없다. 확정 후 이탈로 혼자 남는 것은 실패가 아니라 그대로 진행한다(아래 매칭완료 대기방).
  - **홈 화면 상태는 저장값이 아니라 파생값이다.** 별도 상태 컬럼이나 취소 사유 컬럼을 두지 않고 아래 규칙으로 계산한다.

    | 홈 상태 | 조건 |
    |---|---|
    | 대기 없음 | 활성 `running_players` 없음 |
    | 매칭 대기 중 | 방이 `MATCHING`이고 마감 전 |
    | 매칭 확정 | 방이 `MATCHED` |
    | 매칭 실패 | 방이 `CANCELLED`, 또는 마감이 지났는데 아직 `MATCHING` |

  - 이 네 상태가 `GET /users/me/running-match`의 `state`(`NONE`/`WAITING`/`MATCHED`/`FAILED`)로 그대로 내려간다 — 표시 이름만 다르고 판정 규칙은 같다.

- **매칭 현황 배너**: 대기 중에는 모든 화면 하단에 배너를 고정한다(슬롯 시각·현재 인원·마감까지 남은 시간). 다른 탭으로 이동해도 유지된다.
  - **배너 전용 API를 만들지 않는다** — 필요한 값은 매칭 SSE 스트림에 이미 흐르므로 그대로 쓴다. 같은 정보를 조회 API로 한 번 더 받을 이유가 없다.
  - 따라서 **SSE 연결을 홈 화면 생명주기에 묶지 않아야 한다.**

**매칭완료 대기방**

- 현재 위치 지도: 사용자 위치 지도 표시.
  - **여는 시점은 클라가 계산한다** — 보정된 시각이 `start_at - N분`(N은 설정값)에 도달하면 연다. 타이머·카운트다운·러닝 화면 전환과 같은 방식이다.
  - **서버 신호(SSE 이벤트)를 새로 두지 않는다.** 기준은 "서버만 아는 정보가 바뀌었나"다 — `MATCH_STARTED`는 마감 시점 확정 인원이라 해당하지만, 지도 오픈은 시각만 알면 되고 클라에는 `scheduledStartAt`(`RoomInfo`)과 서버 시각 오프셋이 이미 있다.
- 매칭된 참가자 목록: 닉네임·페이스·소개글 표시.
- 시작 타이머: 러닝 시작까지 카운트다운 — **클라이언트가 돌리되 기준 시각은 서버 값을 쓴다**. 서버가 매초 틱을 보내지 않는다.
  - 기준을 각자 기기 시계로 삼으면 참가자마다 출발이 어긋난다. **서버 시각은 HTTP 응답의 `Date` 헤더로 얻어** 자기 시계와의 오프셋을 구해 보정한다(보정 방식 자체는 미정).
  - **시작 3초 전부터 3-2-1 카운트다운**(화면·음성·햅틱). 이 구간에서는 뒤로가기를 차단한다.
  - 보정된 시각이 `start_at`에 도달하면 클라가 러닝 화면으로 전환하며 WS `RUNNING_START`(C→S)로 시작을 알린다. 서버는 같은 시각에 내부 스케줄러로 `running_rooms.status='STARTED'`로 전환한다 — 클라이언트가 호출하는 REST API는 없다.
- 나가기: 나간 사람만 `running_players.status='MATCHED_LEFT_*'` 처리 + `deleted_at` 기록, 해당 `running_room_sessions` row는 `is_connected=false`. 방은 유지되고 남은 참가자는 계속 대기.
  - **시작 직전까지 나갈 수 있다.** 시각으로 차단하지 않는다 — 막아도 앱을 강제 종료하면 그만이라 실효가 없고(그 경우 이탈로 기록되지 않고 미제출자로 남는다), 늦게 나가는 것은 차단이 아니라 페널티로 다룬다.
- **확정 후 이탈에는 페널티가 붙는다** — 모집이 마감(`close_at`)되고 유예 시간이 지난 뒤에 나가면, 일정 시간 매칭 신청이 제한된다. 한 번이면 걸린다. 판정 방식은 아래 도메인 제약의 이탈 페널티 절에 있다.
  - **유예를 두는 이유**: 마감 직전에 방에 붙은 사람도 확정 통보를 받고 판단할 시간이 있어야 한다. 마감과 페널티 시작 사이의 간격만큼은 **누구에게나 보장된다**.
  - **제재는 우선순위 하향이 아니라 신청 제한이다.** 대기 인원이 적은 동안에는 우선순위를 낮춰도 효과가 없다 — 한 슬롯에 셋이 대기 중이면 순위와 무관하게 그 셋이 매칭된다. 반면 신청 제한은 경쟁 유무와 무관하게 동작하고, 매칭 알고리즘을 건드리지 않는다.
  - **솔로 러닝은 대상이 아니다** — 혼자 그만두는 것은 피해자가 없다. 쿨다운 중에도 막지 않는다. 막으면 서비스를 통째로 못 쓰게 된다.
  - **러닝 중 조기 종료의 제재 정책은 아직 정하지 않았다.** 부상·컨디션 같은 사정이 있을 수 있고 남은 사람은 계속 달릴 수 있어 피해가 작다. 상태값(`RUNNING_LEFT_PENALTY` / `RUNNING_LEFT_NO_PENALTY`)은 지금 확정해두고 — 나중에 넣으면 이미 쌓인 이탈을 되짚을 수 없다 — 당분간 전부 `RUNNING_LEFT_NO_PENALTY`로 기록한다.
  - **취소 안내 문구**: 대기방에서 나가기를 누를 때 제재 구간이면 그 사실을 알린다. "매칭 우선순위가 낮아진다"처럼 실제로 동작하지 않는 안내는 쓰지 않는다.
- **확정 후 이탈로 혼자 남아도 방을 취소하지 않는다** — 솔로 러닝이 이미 1인 방이므로 혼자 뛰는 것 자체가 서비스 안에 있고, 확정 통보를 받고 준비를 마친 사람에게서 러닝을 뺏을 이유가 없다. `type`은 `MATCH`로 남고 결과 화면에 참가자가 한 명으로 나올 뿐이다. 자동 재매칭(빈자리 채우기)은 하지 않는다.
  - **마감 시점과는 구분한다.** 마감(`close_at`)에 2명 미만이면 매칭이 성사되지 않은 것이라 `CANCELLED`로 닫고 실패를 알린다.
  - 모집 중(`MATCHING`) 이탈도 방을 유지한다 — 2명이던 방에서 1명이 빠지면 1인 방으로 돌아가 마감까지 계속 모집한다. 마지막 참가자까지 취소한 경우에만 `CANCELLED`로 닫는다.
- **대기 취소·초대 거절은 row를 지우지 않는다** — `running_players.deleted_at`만 찍는 소프트 삭제라 **취소 시각·당시 상태(`INVITED`=거절 / `JOINED`=취소)·신청 시각이 그대로 조회된다.** 별도 스냅샷 테이블을 두지 않는 이유가 이것이다.
  - **관찰이 가능해야 한다.** "사람이 붙자마자 취소"를 반복하는 패턴이 실재하는지는 데이터가 없으면 판단할 수 없고, 취소는 소급 수집이 불가능하다. 신청→취소 소요 시간은 `created_at`과 `deleted_at`의 차로, 당시 방 인원은 `running_room_sessions`를 거쳐 얻는다.
  - **조회 경로는 오염되지 않는다** — 활성 판정이 `deleted_at IS NULL`을 항상 포함하므로 후보 방 스캔·인원 집계에 삭제된 row가 섞이지 않는다.

### 러닝

**러닝 중 - 메인**

- 위치 지도: 현재 위치·이동 경로 표시.
- 러닝 정보: 페이스·러닝 시간·이동 거리·케이던스 실시간 제공.
- 일시정지: 멈춰 있는 동안 경과 시간과 거리 계산이 멈추고 좌표 전송도 중단한다 — GPS 흔들림이 거리로 잡히면 기록이 부풀려진다.
  - **다른 참가자는 계속 진행한다.** 일시정지는 본인 기록에만 영향을 주며, 상태는 참가자들에게 공유돼 화면에 멈춤으로 표시된다.
  - 종료는 2초 이상 길게 눌러야 한다 — 러닝 중 오조작으로 기록이 끊기는 것을 막는다.
- 사진 촬영: 촬영본은 본인 디바이스 갤러리에만 저장. 서버 업로드/조회 API 없음(results 등 응답에 사진 필드 없음).

**러닝 중 - 다른 유저**

- 유저 트랙: 다른 참가자 진행 상황을 트랙 형태로 표시.
- 유저 비교 정보: 앞뒤 참가자 거리·페이스 정보.
- 음성 코칭: 러닝 화면 상단 mic 아이콘으로 켜고 끈다.
  - **서버는 파티원 비교 이벤트(추월·역전·격차)의 판정과 발신만 한다.** 음성 합성·재생·mute는 전부 클라이언트 몫이다.
  - 판정을 서버가 독점하므로 참가자마다 결과가 갈리지 않는다.
  - 구간별 안내(1km 도달·구간 기록)는 클라이언트가 자기 데이터로 처리한다. 서버가 관여할 이유가 없다.
  - 트리거 조건(판정 기준·격차 임계치)은 미정.

**러닝 후 - 대시보드**

- 본인 경로 확인: 달린 경로 지도 표시.
- 참가자 공통 정보: 참가자별 러닝 시간·이동 거리.
- 참가자 상세 정보: 평균 페이스·소모 칼로리·평균 케이던스·구간별 평균 페이스. 같은 방 참가자끼리는 서로의 상세 기록 열람 가능(본인 제한 없음). GPS 트랙 저장 방식은 2번 도메인 제약 참고.
  - **누적 상승 고도는 참가자 상세에 함께 보여준다** — `total_elevation_gain`이 결과·기록 상세 응답에 `totalElevationGainMeters`로 나간다. 컬러 판정에도 같은 값을 쓴다.
  - **구간별 고저는 순고도차로 보여준다** — 구간마다 `elevation_change`(끝 고도 − 시작 고도)를 저장하고 `elevationChangeMeters`로 내린다. 부호가 그대로 구간 성격이라(오르막 `+`, 내리막 `−`, 평지 0 근처) 오름/내림 분류를 따로 저장하지 않는다.
    - **누적 상승과 순고도차는 다른 값이다.** 기록은 "얼마나 힘들었나"라 올라간 것만 합산하고, 구간은 "어떤 지형이었나"라 오르내림을 상쇄한다. 그래서 구간값을 세로로 더해도 기록의 누적 상승과 맞지 않는다 — 화면에서 총합처럼 보여주지 않는다.
    - **점별 고도는 여전히 넣지 않는다.** 스마트폰 GPS는 수직 오차가 커서 지점 하나의 값은 믿기 어렵다 — 구간 양 끝의 차이는 오차가 상당 부분 상쇄되지만 점 단위는 그렇지 않다. 고도 자체를 GPS 값 그대로 쓸지, 좌표로 외부 고도 데이터를 조회해 보정할지는 **미정**이다.

### 기록

**기록**

- 일정 조회: 캘린더로 러닝 기록 확인 — 러닝한 날을 표시하고, 날짜를 선택하면 그날 기록을 보여준다. 같은 날짜에 기록이 여러 건이면 목록으로 표시한다.
  - 기록 카드에는 **달린 경로 모양을 작게 함께 띄운다** — 거리·시간 숫자만으로는 어느 러닝인지 구분되지 않는다. 목록 응답이 경로를 같이 내려주므로(`routePolyline`) 카드마다 추가 조회가 없다.
  - 날짜별 획득 색 표시는 보류 — 컬러 조건표가 확정되면 입힌다.
- 일정 상세 정보: 선택 일정의 경로·러닝 기록 확인.

> **대회 기능은 서비스에서 제외한다.** 마라톤 일정 조회·북마크는 만들지 않으며, 탭·라우트·테이블·API 어느 것도 두지 않는다. 러닝 기록과 무관한 외부 정보라 빠져도 다른 기능에 영향이 없다.

### 피드 [MVP 제외]

> 인앱 피드·댓글·대댓글·좋아요 전부 해당. 탭·라우트는 등록하고 화면은 준비중으로 대체한다.

**피드 목록 페이지**

- 무한 스크롤 조회, 목록에서 바로 이미지/전체글/좋아요·댓글 버튼 노출.
- 좋아요 버튼: 목록에서 바로 토글.
- 댓글 버튼 → 댓글 모달로 이동.
- 친구 탭: 친구의 게시물 최신순. 공개 범위 필터: 친구의 "친구"/"전체" 공개 피드 + 내 피드 전부.
- 전체 탭: 친구 + 타 사용자 게시물 혼합(인스타 탐색 방식). 초기 버전은 최신순 + 가벼운 가중치(친구의 친구 등), 개인화 추천은 이후 확장. 공개 범위 필터: "전체" 공개 피드 + 친구의 "친구" 공개 피드.
- 프로필 클릭 → 프로필로 이동.
- 게시글 검색: 노출 범위는 "전체" 공개 피드 + 본인 피드만. 사용자 검색은 친구 절로 분리됐다.
- 댓글: 작성/수정/삭제, 답글 작성/수정/삭제, 댓글 좋아요.
  - 수정은 작성자 본인만 가능(피드 소유자는 삭제만). 수정 시 이전 내용은 `delete_comments`에 스냅샷 보관(피드와 동일).
  - 대댓글 depth는 1단계 제한 — `comments.parent_comment_id`가 있는 댓글엔 답글 작성 API 자체를 차단.
  - 답글은 목록에 바로 포함하지 않고 "답글 N개 보기" 탭 시 지연 로딩(인스타그램 방식). 댓글 목록 정렬은 등록순.
  - 삭제 권한: 댓글 작성자 본인 또는 그 댓글이 달린 피드의 소유자(악플/스팸 관리 목적).

**피드 작성 페이지**

- 이미지 업로드: 여러 장 선택해 첨부.
- 글 작성: 텍스트/이미지 둘 다 비운 채 게시 불가 — 최소 하나 필수.
- 노출 범위 선택: 친구/전체/나만.
- 위치/경로 첨부: 별도 기능 아님 — 러닝 기록 템플릿 선택에 통합. 템플릿 카드에 경로 미리보기 지도 포함 — 피드 카드 `record.routePolyline`은 `running_records.route_polyline`의 다운샘플 encoded polyline(별도 API 없음).
- 러닝 기록 템플릿 선택: 과거 기록 선택 시 거리/시간/페이스·경로 미리보기가 카드로 자동 삽입. 대시보드에서 진입한 경우 방금 완료한 기록이 기본 선택.
- 게시 버튼: 등록 후 피드 목록 최상단에 노출.

### 프로필·설정

**프로필 페이지**

- 프로필 요약: 사진, 닉네임, 소개글, 마일리지, 최고 페이스, 러닝 횟수, 친구 수 표시.
  - 세 지표 모두 별도 저장 테이블 없이 `running_records`에서 계산한다 — **마일리지**(`total_distance` 합산, 전체 누적과 월 누적을 구분해 제공), **최고 페이스**(`MIN(avg_pace)`), **러닝 횟수**(`COUNT(*)`).
  - 전체 사용자 대비 백분위는 표시하지 않는다 — 순위 집계 배치가 필요한데 초기에는 표본이 적어 수치가 무의미하다.
- 컬렉션: 획득한 색을 보유 수 / 전체 수와 함께 표시.
  - **못 얻은 색도 함께 보여준다** — 획득 조건 문구와 같이 표시해 "무엇을 더 모을 수 있는지"가 드러나야 한다.
  - 컬렉션은 하나뿐이다. 블렌드 컬렉션은 없다.
- 친구 수 클릭 → 친구 목록 페이지로 이동(**본인 프로필에서만**). 타인 프로필에서는 수만 보이고 목록은 열리지 않는다.
- 편집 버튼 → 프로필 편집 페이지로 이동.
- 설정 버튼 → 설정 페이지로 이동.
- 조건부 표시: 본인 프로필이면 편집/설정 버튼, 타인 프로필이면 친구 요청 버튼.
- 비공개 정보 처리: **지인 마스킹**(`users.profile_visibility=FRIENDS`) — 친구가 아닌 타인에게는 컬렉션을 가린다(`403 PROFILE_PRIVATE`). 사진·닉네임·소개글·마일리지·최고 페이스·러닝 횟수·친구 수는 항상 공개.
- **[MVP 제외]** 내가 올린 피드 그리드: 프로필 하단에 본인 작성 피드를 썸네일 그리드로 표시.
- **[MVP 제외]** 피드 작성 버튼: 누르면 피드 작성 페이지로 이동.
- **[MVP 제외]** 피드 편집: 게시글 수정/삭제, 노출 범위 설정.
- **[MVP 제외]** 신고/차단 메뉴.

**프로필 편집 페이지**

- 사진 변경, 닉네임 변경(서비스 전반 표시 갱신), 소개글 변경. 셋은 저장 흐름이 달라 API를 나눈다.
  - **사진**: 업로드 URL 발급 → S3 직접 업로드 → 키 반영의 3단계라 사진을 고르는 시점에 처리된다(저장 버튼과 무관). 삭제도 별도 동작이며, 삭제는 S3 객체를 남기고 DB의 키 연결만 끊는다.
  - **닉네임**: `user_onboardings`에 저장되므로 온보딩을 마쳐야 바꿀 수 있다. 남이 쓰고 있으면 `409 NICKNAME_ALREADY_EXISTS`, 현재 닉네임과 같으면 아무것도 바꾸지 않는다. 저장 전 중복 확인 API로 입력 중에 미리 알려주되, 확인과 저장 사이에 선점될 수 있어 최종 방어는 저장 시점의 409다.
  - **소개글**: 별도 검증이 없어 프로필 수정 API에서 처리한다.

**친구 목록 페이지**

- 친구 목록 조회, 이름 기준 검색. **본인 목록만 본다** — 타인의 친구 목록은 열지 않는다. 친구의 친구를 훑어 사람을 찾는 흐름이 없고(사람 찾기는 사용자 검색), 누구와 친구인지는 민감한 정보다.
- 받은 친구 요청 확인 및 수락·거절. 보낸 요청 목록 화면은 두지 않는다.
  - **친구는 요청 → 수락으로 성립하는 대칭 관계다.** 성립한 뒤로는 누가 요청했는지에 의미가 없다.
  - 서로 요청을 주고받으면(A→B 요청 중에 B→A 요청) **바로 성립한다** — 이미 합의된 상황이라 한 번 더 수락을 요구하지 않는다.
  - 거절·요청 취소·친구 삭제는 모두 관계를 지운다. **이력을 남기지 않는다.**
- 사용자 클릭 → 해당 사용자 프로필로 이동.
- **사용자 검색**: 닉네임으로 전체 사용자를 찾는다(`GET /users/search`) — 친구를 추가하려면 먼저 사람을 찾아야 하므로 친구 기능의 진입점이다. 친구 목록 안의 이름 필터와는 대상이 다르다.

**설정 페이지**

- 계정: 이메일과 로그인 수단을 표시한다(`GET /users/me/account`). 이메일을 보여주는 화면은 여기뿐이다.
  - 로그인 수단은 `oauth_users` row 유무로 가른다 — 있으면 그 provider, 없으면 로컬.
  - **소셜 계정**: "구글/카카오 계정으로 로그인 중"을 표시하고 비밀번호 변경 항목을 감춘다 — 어느 provider로 가입했는지 잊으면 다른 소셜 버튼을 눌러 별개 계정이 만들어진다.
  - **로컬 계정**: 로그인 수단 문구 없이 비밀번호 변경 항목만 노출한다. 바로 위에 이메일이 떠 있고 그 항목의 존재 자체가 이미 로컬이라는 표시다. "로컬 계정"은 내부 용어이므로 화면에 쓰지 않는다.
- 비밀번호 변경: **로컬 계정만.** 현재 비밀번호로 본인을 재확인하고 새 비밀번호를 받는다(가입과 같은 규칙 — 6~16자, 영문·숫자·특수문자 각 1자 이상. 확인 일치 검증은 클라).
  - 소셜 계정은 비밀번호가 없어 변경 대상이 아니다. 클라가 항목을 감추더라도 서버가 `409 PASSWORD_NOT_SET`으로 막는다 — 구버전 앱과 직접 호출이 있다.
  - 변경해도 다른 기기 세션은 끊기지 않는다. 전 기기 로그아웃은 **[MVP 제외]**.
  - **비밀번호 찾기(로그인 전 재설정)는 없다** — 초기 페이지에 "비밀번호를 잊으셨나요" 진입점을 두지 않는다. 이 기능은 로그인된 상태에서만 쓴다.
- 알림 설정: 전체 알림 on/off 단일 토글(`users.alert_consent` — 매칭 확정·실패, 러닝 시작 리마인더, 친구 요청 도착·수락 네 종류 전부 관장). 종류별 개별 토글은 **[MVP 제외]**.
  - **기본값은 on**(`default true`) — 넷 다 거래성 알림이라 별도 수신 동의 대상이 아니고, 가입 직후부터 매칭 확정 푸시가 도달해야 한다.
  - 앱 내 토글은 OS 알림 권한과 별개다. 둘 중 하나라도 꺼져 있으면 푸시가 도달하지 않는다.
- 프로필 공개 범위 설정: `users.profile_visibility`(지인 마스킹 on/off).
- **피드 기본 공개 범위 설정은 두지 않는다.** 공개 범위(`feeds.visibility`)는 피드마다 개별 선택하고, 작성 화면의 기본 선택값은 클라이언트가 PUBLIC으로 고정한다 — 사용자별 기본값을 서버에 저장할 이유가 없다.
- 로그아웃/회원탈퇴: 확인 팝업 후 처리.
  - 로그아웃: `POST /auth/logout`(바디 없음 — 서버가 요청 토큰으로 본인 식별). 해당 access 토큰을 서버 블랙리스트에 올려 즉시 무효화 — 만료 전이라도 그 토큰 요청은 `401 TOKEN_BLOCKED`
  - 로그아웃 시 기기 단위 푸시 중단(`is_active=false`)은 하지 않는다 — 토큰 블랙리스트만. **[MVP 제외]**로 두고, 필요해지면 로그아웃 요청에 `deviceId`를 받아 처리한다. `device_id` 컬럼과 `POST /devices`는 MVP에 포함된다.

### 공통 (특정 화면 소속 아님)

**알림 (푸시)**

- 매칭 확정/실패, 러닝 시작 리마인더, 친구 요청 도착·수락 — 알림 종류별로 눌렀을 때 최적 화면으로 랜딩.
- **[MVP 제외]** 피드 좋아요/댓글.
- 인앱 알림함(목록 조회 화면) 없음 — 푸시로만 발송, 클릭 시 랜딩만 수행. `notification` 테이블/조회 API 불필요, 디바이스 등록(`user_devices`) API만 유지.

## 2. 도메인 제약

> 전체 테이블·컬럼·타입·PK 규칙·enum·단위는 `erd.md`가 단일 출처. 여기서는 API 작성·구현에 필요한 도메인 제약과 설계 맥락만 남긴다.

**API 리소스 네이밍**: 방을 가리키는 이름은 DB·API·팀 대화 모두 **`room` 하나로 통일한다**(`running_rooms` ↔ `runningRoomId` ↔ `/running-rooms`).

- **"세션"은 방을 가리키는 말로 쓰지 않는다.** 이 단어는 로그인 세션·WebSocket 세션에 이미 쓰이고 있어 겹친다. 러닝을 서술할 때는 "러닝 구간", 방을 가리킬 때는 "방"으로 적는다.
- **`running-match`와 `running-room`은 다른 단계다.** 전자는 매칭 신청·대기(`running_players`), 후자는 확정된 방과 그 이후(`running_rooms`)를 가리킨다.
- 신청 즉시 방이 생기므로 `runningRoomId`는 매칭 단계에서도 존재한다. 다만 **경로 체계는 단계로 갈린다** — 매칭 단계는 방 ID를 URL에 쓰지 않고(`GET /users/me/running-match`), 방 단계는 반드시 쓴다(`GET /running-rooms/{runningRoomId}/results`).

**매칭·러닝 설계**: 구간마다 통신 방식이 다르다 — **매칭은 REST + SSE**, **러닝 구간은 WebSocket**(`/ws/running-rooms`)이다.

- 매칭 구간은 클라가 보내는 것이 신청·취소 둘뿐이라 양방향 채널이 필요 없다 — REST로 보내고 현황은 SSE 스트림(`/running-matches/stream`)으로 받는다. 러닝 구간은 위치를 주기 발신하는 고빈도 양방향 구간이라 WebSocket을 쓴다.
- 매칭 시작 = `running_players` 생성 + **1인 방(`running_rooms`, `type='MATCH'`) 생성**. 매칭은 "대기 풀에서 사람을 모아 방을 만드는" 것이 아니라 **모집 중인 방끼리 합치거나 신청자를 기존 방에 붙이는** 것이다. 대기 인원·성사·취소는 SSE 이벤트로 전달된다(전문은 `api-spec.md` 5번).
- **SSE 연결은 화면 생명주기에 묶지 않는다.** 매칭 대기 중 현황 배너가 모든 화면에서 유지돼야 하므로 홈을 벗어나도 스트림은 살아 있어야 한다. 이는 클라이언트 아키텍처 제약이다.
- 매칭 이벤트는 전부 **전체 상태를 담는다** — 놓친 이벤트를 되짚을 필요가 없어 재연결은 곧 스냅샷 재수신이다. 앱 재시작처럼 스트림이 끊긴 뒤에는 `GET /users/me/running-match`가 같은 정보를 돌려준다.
- **SSE → WS 전환**: `start_at` 직전에 WS를 연결하고, 도달 시 `RUNNING_START`를 보낸 뒤 `RUNNING_STARTED` ack를 받고 나서 SSE를 닫는다. ack 전에 닫으면 WS 연결 실패 시 돌아갈 채널이 없다.
- 러닝 시작은 클라 주도(`RUNNING_START` C→S)이나 카운트다운 기준 시각은 서버 값을 쓴다. 메시지 네이밍 규칙: 클라 발신 현재형 / 서버 발신 과거형.
- 매칭 성사 후에는 `runningRoomId`(Long)로 REST 호출(결과 조회).

**`user_devices.is_active`**: 로그인 시 디바이스 등록/갱신 API가 `is_active=true`로 전환(푸시 준비). 기기 단위 비활성화(로그아웃 시 false)는 **[MVP 제외]** — 로그아웃은 토큰 블랙리스트만 처리하고 `deviceId`를 받지 않는다.

**이미지 업로드**(`feed_images`, `users.profile_image_key` 등 전체 공통): Presigned URL 방식 — 클라이언트가 업로드용 presigned URL 요청 → 서버가 S3 presigned URL 발급 → 클라이언트가 S3에 직접 업로드 → 반환받은 key를 본 API(피드 작성, 프로필 사진 변경 등) 요청에 포함해 전달.

**GPS 트랙**: 원본 트랙은 Postgres 테이블이 아님 — `running_records.gps_track_key`로 S3 객체를 참조. **매칭 러닝과 솔로 러닝이 같은 경로를 쓴다.**

- 클라이언트가 1~2초 간격으로 좌표를 수집해 **로컬에 쌓으면서** 10초마다 모아서 WS로 보낸다. 서버는 Redis(`runningRoomId+userId` 키)에 버퍼링하고, 종료 신호(WS `RUNNING_FINISH`) 수신 시 S3에 업로드하며 `running_records`를 저장한다.
- **거리·페이스·구간 분할은 서버가 받은 좌표로 계산한다.** 클라이언트 계산값은 러닝 중 화면 표시용이지 저장값이 아니다.
- **화면에 그리는 경로는 S3가 아니라 DB에서 나간다.** 종료 시 원본 트랙을 다운샘플해 `running_records.route_polyline`(encoded polyline)을 함께 저장하고, 대시보드·기록 목록·기록 상세는 이 값만 쓴다. S3 원본은 재계산·분석용으로 남는다.
- **좌표에는 고도를 포함한다.** 화면에 쓰지 않더라도 원본에 있어야 누적고도·경사를 나중에 소급 계산할 수 있다 — 없으면 지형 API로 채워야 하고 그건 실측이 아니다.
- **연결이 끊겼다 돌아오면 못 보낸 구간부터 이어 보낸다.** 클라이언트는 마지막으로 전송에 성공한 순번을 기억했다가 재연결 후 그 다음부터 다시 보내고, 서버는 이미 가진 순번을 무시한다. 그래서 로컬 사본은 종료할 때까지 지우지 않는다.
  - **한계**: 러닝이 끝날 때까지 연결이 돌아오지 않으면 종료 신호조차 보낼 수 없어 그 기록은 잃는다. 필요해지면 REST 폴백을 붙인다.
- **솔로 러닝도 방을 만든다.** 매칭을 거치지 않을 뿐 `running_rooms`(`type='SOLO'`)·`running_players` 행이 생기고(개시 즉시 `STARTED`), 같은 WS를 쓴다 — 솔로만 다른 식별자를 쓰면 WS 메시지 스키마가 두 벌이 된다. 클라이언트가 만들 수 있는 방은 솔로뿐이며 매칭 방은 서버가 만든다.

**컬러 시스템**: 러닝 지표가 조건을 충족하면 고정 팔레트의 색이 열리는 **잠금 해제 모델**이다. 색을 새로 만들어내지 않는다.

- 생성 모델을 쓰지 않는 이유는 수집이 성립하지 않기 때문이다 — 색 공간이 무한하면 같은 5km를 100번 뛴 결과가 비슷한 색 100개로 쌓인다. **시그니처 컬러도 블렌드 색도 없다** — 사용자가 색을 고르는 지점이 서비스 어디에도 없다.
- 마스터(`colors`)는 운영이 채워 넣는 고정 데이터이고, 획득 이력(`user_colors`)은 복합 PK라 **같은 색을 두 번 얻는 상황이 없다**.
- 12범주 × 셰이드 3~4로 구성하되 **총 색 개수는 명세에 적지 않는다.** 진행률은 마스터 행 수로 계산하므로 색을 추가해도 코드가 바뀌지 않는다.
- **획득 조건은 DB에 두지 않는다.** 조건의 축이 제각각이라(단일 러닝 거리 / 누적 거리 / 페이스 …) 데이터로 표현하기 어렵다 — 판정은 서버 로직에, DB에는 안내 문구만 둔다.
- **범주별 획득 조건표는 미정이다.** 기획 산출물이 나와야 지급 로직을 짤 수 있다 — 그전까지는 테이블과 조회만 성립하고 색이 열리지 않는다.
- **조건표보다 관측값을 먼저 쌓아둔다.** `total_elevation_gain`과 날씨(`weather_code`·`temperature`)는 지금부터 저장한다 — 조건표가 확정된 뒤에 모으기 시작하면 그전 기록은 판정 대상에서 빠지고, 소급하려면 기록마다 좌표·시각으로 과거 날씨를 다시 조회하는 배치가 필요하다.

**피드-러닝 기록 연결**: `feeds.running_record_id`는 `running_records` 참조 — 피드 작성 시 "러닝 기록 템플릿 선택"에 대응. nullable — 러닝 기록 없이 글+사진만으로도 작성 가능.

**피드 공개 범위**: `feeds.visibility` 값은 3종(친구/전체/나만) — "나만"은 본인 피드 목록/프로필 그리드 조회 시에만 노출, 친구 피드·전체 피드 조회에서는 제외.

**날씨**: 홈 화면 날씨는 클라이언트가 키리스 무료 날씨 API(예: Open-Meteo)를 직접 호출 — 서버 API 없음. 유료 제공자·캐싱 필요 시점에 프록시 추가 재검토.

- **기록에 남기는 날씨는 이것과 별개다.** 러닝 종료 시 서버가 시작 좌표·시각으로 날씨를 조회해 `running_records.weather_code`(WMO 4677 코드)·`temperature`(섭씨)에 저장한다. 컬러 `ADVERSITY`(악조건극복) 판정에 쓰는 값이라 클라이언트 신고값을 쓸 수 없다 — 거리·페이스를 서버가 계산하는 것과 같은 이유다.
- 화면에는 표시하지 않고 응답에도 싣지 않는다 — 저장만 하고 컬러 판정에만 쓴다. 같이 저장하는 `total_elevation_gain`은 `totalElevationGainMeters`로 응답에 나가지만 날씨는 보여줄 화면이 없다.
- 조회 실패는 null이며 종료 처리를 막지 않는다. 그 기록은 악조건 판정 대상에서 빠질 뿐이다.

**`running_rooms.type`**: SOLO/MATCH/INVITE. 방의 성격 축으로, 생성 시 정해지고 바뀌지 않는다. 신청 즉시 1인 방을 만드는 구조라 솔로 방·매칭 대기 방·초대방이 형태(인원 1)로는 구분되지 않아 별도 컬럼이 필요하다 — `max_player_count`(자리 수)나 `status`(어디까지 진행)로는 대체되지 않는 축이고, 값이 셋이라 boolean `is_solo`로도 안 된다. 랜덤 매칭 후보 스캔은 `type='MATCH'`만 보므로 솔로 방과 남의 초대방에 모르는 사람이 배정되지 않는다. `INVITE`는 친구 초대가 후순위 구현이라 아직 쓰이지 않지만 값은 지금 확정한다 — 나중에 넣으면 이미 쌓인 방 데이터를 되짚어야 한다.

**`running_rooms.status`**: MATCHING/MATCHED/STARTED/FINISHED/CANCELLED. 매칭 취소 시 `status='CANCELLED'`만 사용 — 취소 이력도 조회 가능해야 하므로 목록에서 제외하지 않음. `deleted_at`은 별도 용도(예: 관리자의 부정 방 숨김 처리)로 남겨두고 이번 명세에서는 다루지 않는다.

**이탈 페널티 판정**: 제재 대상 여부는 이탈 시점에 정해 `status`에 굳히고(`close_at` + 유예를 지났으면 `MATCHED_LEFT_PENALTY`, 아니면 `MATCHED_LEFT_NO_PENALTY` — 솔로 방 제외), 신청 시점에는 그 값만 본다. `status IN ('MATCHED_LEFT_PENALTY','RUNNING_LEFT_PENALTY')`인 이탈 중 가장 최근 것을 찾아 `deleted_at + 쿨다운`이 아직 안 지났으면 `409 MATCH_COOLDOWN`으로 막는다. 방·마감 시각을 조인할 필요가 없고, `(user_id, status, deleted_at)` 인덱스로 대부분 0행에서 끝난다.

- 세 값은 운영 설정으로 뺀다 — **모집 마감 오프셋**(`close_at = start_at - 오프셋`), **유예**, **쿨다운**. 문서에 숫자를 박으면 조정할 때마다 명세 세 곳을 왕복해야 한다.
- **유예는 마감 오프셋보다 작아야 한다.** 같거나 크면 확정되자마자 페널티 구간이 되어, 마감 직전에 붙은 사람이 판단할 시간 없이 제재받는다. 오프셋에서 유예를 뺀 만큼이 곧 "누구에게나 보장되는 판단 시간"이다.
- **판정 결과를 저장하는 대가**: 유예를 조정해도 이미 쌓인 row는 옛 기준으로 남는다. 쿨다운 길이는 조회 시점 설정을 쓰므로 그쪽은 즉시 반영된다.
- **`deleted_at`이 이탈 시각이다.** `updated_at`은 그 row가 한 번만 더 갱신돼도 값이 밀려 쿨다운이 잘못 계산된다.

**개인 단위 진행 상태**: `running_players.status`가 갖는다 — 러닝 중이면 `RUNNING`, 완주하면 `COMPLETED`다. `running_records` 행은 종료 처리의 산물이라 `COMPLETED` 전환과 같은 트랜잭션에서 만들어진다.

**유효 러닝 판정**: 기록은 **무조건 저장하고**, 유효 여부는 저장하지 않고 조회 시 계산한다. 최소 거리·최소 시간에 미달하는 기록을 통계에서 빼기 위한 것이다.

- 두 값(**최소 거리**, **최소 시간**)은 운영 설정으로 뺀다 — 이탈 페널티의 세 값과 같은 이유다.
- **미달이어도 `running_records`는 저장한다.** 저장을 건너뛰면 `status`가 `COMPLETED`로 넘어가지 못해 방이 전원 제출로 닫히지 못하고 타임아웃까지 `STARTED`로 남는다.
- **유효 여부를 컬럼에 굳히지 않는다** — `total_distance`·`total_duration`은 사실이라 변하지 않지만 임계값은 정책이라 바뀐다. 저장하면 값을 조정할 때 이미 쌓인 row가 거짓이 된다.
- **제외 대상**: 프로필 요약의 마일리지·최고 페이스·러닝 횟수와 컬러 획득 판정. 특히 최고 페이스는 `MIN(avg_pace)`라 왜곡이 크다 — 몇십 초 뛰다 멈춘 기록 하나가 그 사람의 최고 페이스가 된다.
- **포함 대상**: 본인 기록 목록·캘린더·러닝 후 대시보드. 자기가 뛴 사실 자체는 보여야 하고, 피드 템플릿으로도 쓸 수 있다.

**`STARTED`→`FINISHED` 전환**: 둘 중 먼저 오는 시점에 자동 전환 — ① `RUNNING` 참가자 전원이 기록 제출(`COMPLETED`) 완료 시 즉시 `FINISHED`, ② 미제출자가 있어도 시작 후 서버 설정 시간 경과 시(타임아웃) 스케줄러가 `FINISHED` 처리. 타임아웃 값은 운영 정책.

**`running_players.status`**: 신청부터 완주까지를 한 축으로 표현한다. 기본값은 `JOINED` — 매칭 버튼을 누른 순간이 곧 참가 의사 표명이다.

| 값 | 뜻 |
|---|---|
| `INVITED` | 친구 초대를 받았고 아직 응답하지 않음. 활성 신청이 아니다 |
| `JOINED` | 참가 |
| `MATCHED_LEFT_PENALTY` / `MATCHED_LEFT_NO_PENALTY` | 확정 후 이탈 — 제재 대상 여부로 갈린다 |
| `RUNNING` | 러닝 중 |
| `RUNNING_LEFT_PENALTY` / `RUNNING_LEFT_NO_PENALTY` | 러닝 중 이탈 — 제재 기준은 미정이라 당분간 전부 `NO_PENALTY` |
| `COMPLETED` | 완주 |

- **매칭 진행 단계는 이 컬럼에 넣지 않는다**(`WAITING`·`FAILED` 등). 그건 `running_rooms.status`가 갖는다 — 같은 사실이 두 곳에 저장되면 방 상태가 바뀔 때마다 참가자 전원을 갱신해야 하고 드리프트가 생긴다.
- **"끝난 시각"은 `deleted_at`이 갖는다.** 완주(`COMPLETED`)는 정상 종료라 `deleted_at`이 null이다.

**목표 거리 vs 실제 거리**: 이름으로 갈린다 — **목표는 `target_*`**(`running_players.target_distance` = 신청 시 고른 3/5/10km, `running_rooms.target_distance` = 방의 조건), **실제 이동 거리는 `total_*`**(`running_records.total_distance` = 러닝 종료 후 확정). 테이블을 몰라도 컬럼명만으로 구분된다. API도 같은 규칙이다(`targetDistanceMeters` / `totalDistanceMeters`).

**회원탈퇴 시 연관 데이터 처리** (테이블별):

- **유지**: `feeds`, `comments`, `running_records`(+`running_splits`) — 같은 방 참가자의 대시보드 기록 비교가 서비스 핵심이라 탈퇴해도 기록은 유지. 해당 테이블들의 `user_id` FK는 하드delete 이후에도 값이 남아야 하므로 DB 레벨 CASCADE 걸지 않고 애플리케이션 레벨에서 처리. 작성자가 탈퇴한 경우 응답의 작성자 정보는 `{ userId, nickname: "탈퇴한 사용자", profileImageUrl: null, isDeleted: true }`로 대체(고정 문구 — 실제 닉네임은 스냅샷 안 하므로 조회하지 않음).
- **유지 (카운트 재계산 안 함)**: `feed_likes`, `comment_likes` — 탈퇴자가 누른 좋아요는 남겨두고 `like_count` 그대로(인스타그램 방식).
- **즉시 삭제**: `friendships`(`ON DELETE CASCADE` — 친구 목록·받은 요청 목록에서 탈퇴 유저 노출 방지. 요청·수락 어느 쪽이든 삭제), 개인 데이터 테이블 전부 — `user_onboardings`, `user_devices`, `oauth_users`, `running_players`(+`running_room_sessions` CASCADE), `user_colors`(획득 컬러 이력)
- 친구 수는 집계 컬럼이 아니라 `friendships` COUNT라 **재계산이 필요 없다** — row가 사라지면 수도 함께 줄어든다. (`feed_likes`는 row를 유지해 카운트도 유지 — 기준이 다름.)

**삭제 처리 방식** (리소스별로 다름 — API 설계 시 각각 구분해서 반영):

- **`users`**: 하드delete + 아카이브 — 실제 DELETE 전에 `delete_users`에 스냅샷 먼저 저장(감사/로그 용도, 복구 기능 없음).
- **`feeds`**: `deleted_at` 소프트delete(복구 가능·조회 제외 처리).
- **`comments`**: 답글 유무로 분기(레딧 방식, 두 경우 모두 `delete_comments` 스냅샷 먼저 저장) — 답글 없으면 하드delete, 답글 있으면 톰스톤(row 유지 + 내용 비움 + `deleted_at` 기록, "삭제된 댓글입니다" 자리표시로 노출하고 답글 스레드 유지).
