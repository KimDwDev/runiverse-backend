# 결정 기록

메인 서버(running-service)·러닝 세션 서버·AI 전용 서버와 그 아래 플랫폼에 대해 정한 것, 버린 것, 뒤에 바뀐 것을 한곳에 날짜순으로 남긴다. 범위가 서로 얽혀 있어(예: 예산 결정이 EKS 데이터 배치를 뒤집는다) 서비스마다 따로 두지 않는다. 설계 문서는 지금 설계만 보여 주고, 왜 그렇게 됐는지는 이 기록의 항목으로 링크한다.

| 무엇 | 어디 |
|---|---|
| 전체 지도 · 서비스 이름 · ID 규칙 | [README.md](README.md) 「서비스 이름」 「문서 규칙」 |
| 러닝 세션 분리 — 이유 · 구조 · 검증 · 옮기기 | [running-session-server/README.md](running-session-server/README.md) |
| 단계 진행 상태 | [running-session-server/README.md](running-session-server/README.md) 「진행 단계」 |
| AI 전용 서버 | [ai-server/README.md](ai-server/README.md) |
| 데이터 · 인프라 / EKS | [platform.md](platform.md) · [eks.md](eks.md) |

> 주소·키·비밀값은 적지 않는다 — Parameter Store 이름까지만.

- **상태** — `정함`: 팀이 정했다. `제안`: 설계 검토에서 권한 안이고 아직 확정하지 않았다 — 확정하면 상태 줄만 `정함`으로 바꾼다. `바뀜 → D-yy`: 뒤 항목이 바꿨다. `버림`: 대신할 결정 없이 접었다. 상태 줄의 `정하지 않음`은 그 결정이 일부러 남긴 빈칸이고, 답은 링크한 문서의 「정하지 않은 것」에서 기다린다.
- **번호는 다시 쓰지 않는다** — 바뀐 항목도 지우지 않는다. 본문은 고치지 않고 상태 줄만 고친다(날짜와 양쪽 링크).
- **러닝 세션 저장소의 자기 기록은 `RS-D-01`부터** — 저장소를 나눈 뒤 세션 안에서만 뜻이 있는 결정(내부 구조·라이브러리)은 그 저장소에 `RS-D-` 번호로 적는다. 서비스 사이·플랫폼 결정은 계속 여기에 `D-` 번호로 적는다.
- **범위** — `AI` · `세션` · `메인` · `플랫폼` · `공통`(서비스 둘 이상) · `문서`.

## 적는 법

```text
### D-nn 제목 (YYYY-MM-DD)

`범위` · **상태** — 상태에 붙는 한 줄 (바꾼 항목, 정하지 않은 부분)
- **결정** — 고른 것. 바뀌는 표(키 목록·호출 목록·임계값)는 옮기지 않고 그 표의 문서에 링크한다
- **버린 대안** — 대안 — 버린 이유 (대안마다)
- **이유** — 근거 문서의 「절」. 숫자는 run id·PR·커밋으로 가리킨다
- **영향** — 이 결정으로 고치는 문서
```

- 결정을 먼저 적고, 같은 PR에서 설계 문서를 고친다.
- 다른 항목을 바꾸면 양쪽 상태 줄에 서로를 적는다 — 바뀐 쪽 `바뀜 → D-yy`, 바꾼 쪽 `D-xx를 바꾼다`.
- 임계값은 [load_test/msa/PREREG.md](../../load_test/msa/PREREG.md)에만, 측정 숫자는 RESULTS 파일에만 둔다.
- 버린 대안 · 영향이 없으면 그 줄을 쓰지 않는다.

## 분리 전 결정 (10-15 ~ 11-23)

### D-01 러닝 실시간 상태는 Redis EC2 + AOF (2026-10-15)

`플랫폼` · **정함** — D-49가 서비스마다 한 대로 이어받는다
- **결정** — 러닝 중 상태(트랙·거리·상태·콤보)는 EC2 Redis에 두고 AOF(`appendonly yes`, `appendfsync everysec`)를 켠다. RDS 상태 어댑터 4개(`infrastructure/persistence/running/state/*DbAdapter`)는 `@Profile("state-db")`로 꺼 둔 채 남긴다(a0cc1aaf, 10-17). 운영 Redis에는 10-23에 적용했다.
- **버린 대안** — 상태를 RDS로 옮기기 — pub/sub 때문에 Redis는 어차피 남아 비용이 줄지 않고, load-1000에서 커넥션 풀을 다 썼다(run 53) / AOF 없이 두기 — Redis를 죽이자 러닝 상태가 에러 없이 사라졌다(run 16)
- **이유** — [load_test/RESULTS.md](../../load_test/RESULTS.md) 「결론」, 「AOF 적용 후 재검증 (run 18)」
- **영향** — load_test/RESULTS.md 「권장」, [platform.md](platform.md) 「Redis」

### D-02 음악 S3 key는 서버가 정해 요청한다 (2026-11-08)

`AI` · **바뀜 → D-07**
- **결정** — 기록 카드 음악은 AI가 만든다. 서버가 음악 S3 key를 정해 요청에 싣고, AI가 그 key에 올린 뒤 완료를 알린다. 음악마다 `PENDING`·`READY`·`FAILED`.
- **이유** — 기록 카드 도메인 첫 설계
- **영향** — api-spec 8·9장, erd `record_card*`

### D-03 메인과 AI는 Kafka 양방향으로만 주고받는다 (2026-11-09)

`AI` · **정함**
- **결정** — 요청 토픽과 완료 토픽 두 방향 모두 Kafka다. 메인은 AI 서버나 SageMaker를 직접 부르지 않는다.
- **버린 대안** — 백엔드가 S3에 올리고 `InvokeEndpointAsync` + SNS로 결과를 받는 잠정안 — 메인이 AI 추론 경로를 직접 다루게 된다
- **이유** — 요청 하나가 여러 곡을 오래 만들고, 주인과 런타임이 다르며, 한쪽이 멈춰도 다른 쪽이 돈다. 서버가 나뉠 수 있어 잠시 보류했다가 같은 날 정했다 ([ai-server/rationale.md](ai-server/rationale.md) 「긴 비동기 생성」)
- **영향** — api-spec 9-5, [README.md](README.md) 「통신 — 어디로 무엇이 지나가는가」

### D-24 러닝 기록의 정본은 러닝 DB, 메인은 사본 (2026-11-24)

### D-44 탈퇴 saga의 단계 (2026-11-24)

`공통` · **정함** (11-25, D-70) — 단계 · 기점 · 보상을 확정했다. 4단계의 '사용자 삭제 이벤트'는 D-72가 사용자 변경 이벤트(삭제 여부 포함)로 묶었다. 지금 탈퇴 경로와 맞추는 법, 메시지 경로 · 본문 · 멱등 키는 정하지 않음 (consistency 「정하지 않은 것」)
- **결정** — 메인이 지휘한다: 사용자를 DELETING으로 표시 → 넘기기 전 메인 상태를 정리 → 세션에 동기 정산 요청(되돌리지 않는 기점) → 메인이 삭제하고 사용자 삭제 이벤트를 아웃박스에 쓴다 → 세션이 모든 인스턴스의 소켓을 닫는다. 기점 전에 실패하면 DELETING을 풀고 지금의 503 `ACCOUNT_DELETION_UNAVAILABLE`로 답하고, 기점 뒤에는 앞으로 재시도한다.
- **버린 대안** — 세션이 혼자 달리기 방을 만들기 — 예약 saga가 늘어난다
- **이유** — 넘길 때 몸무게·프로필을 스냅샷으로 넘겨 정산에 사용자 행이 필요 없다

### D-64 끝내기 폭주는 속도가 아니라 격리로 잰다 + 매칭↔러닝 정합성 (2026-11-25)

`세션` · **정함** — D-57의 SC9 · SC10을 바꾸고 SC14를 더한다. 버린 대안의 이유('끝내기를 새 엔진에서만 고친다', D-63)는 D-79가 바꿨다 — A′에도 F1이 들어가 고친 효과는 A vs A′로, 나눈 효과는 A′ vs B2의 격리로 잰다. 결정은 그대로다
- **결정** — 끝내기 폭주(G4)를 '나누니 빨라졌다'의 근거로 쓰지 않는다. 나눈 효과는 격리로 잰다 — 세션을 용량 이상으로 몰아도 메인(매칭 · 7-1 등)이 평소와 같은가(SC9), 메인을 포화시켜도 러닝이 평소와 같은가(SC10). 둘 다 G3에 넣는다. 매칭↔러닝 경계의 정합성 — 넘기기가 시작 전에 닿는가, 시작 뒤 나가기와 시작이 겹칠 때 하나로 정해지는가, 끝낸 직후 다시 신청할 수 있기까지 — 을 SC14로 잰다.
- **버린 대안** — 끝내기를 고친 모놀리스(A′)와 분리(B2)의 속도 비교 — 끝내기를 새 엔진에서만 고치므로(D-63) 고친 효과와 나눈 효과가 섞인다

- **영향** — [running-session-server/verification.md](running-session-server/verification.md) 「보조 시나리오 SC0 · SC8–SC14」 「판정과 결과」, [load_test/msa/PREREG.md](../../load_test/msa/PREREG.md) SC9 · SC10 · SC14, rationale 「G3 장애 격리」 「G4 끝내기 폭주는 고칠 결함」

### D-68 메인 사본은 지금 `running_records` · `running_segments`를 그대로 쓴다 (2026-11-25)

`메인` · **정함** — architecture 「메인 사본과 반영」의 모양
- **결정** — 메인 inbox가 러닝 결과 이벤트를 받아 지금 있는 `running_records` · `running_segments`에 쓴다. 이 테이블은 분리 뒤 메인 쪽 사본이고 정본은 러닝 DB다(D-24). `record_cards.running_record_id` FK(`ON DELETE CASCADE`)와 카드 쓰기의 `lockOwnedBy` 잠금, 7-1 · 9-5가 읽는 곳은 바꾸지 않는다. 구간(`running_splits`)과 콤보는 새 기록부터 사본에 두지 않는다 — 6-2는 세션이 응답한다(D-58).
- **버린 대안** — 사본 전용 새 테이블(`running_record_summaries` 등) — 카드 FK · 잠금 · 읽는 곳을 모두 옮기는 손 DDL과 코드 수정, 옛 기록 이전이 필요하다
- **이유** — 기록은 쓰고 나면 바뀌지 않는다. 지금 테이블을 그대로 쓰면 메인 쪽에 바꿀 것이 거의 없다
- **대가** — 러닝 DB와 메인 DB에 같은 이름의 테이블이 생긴다. 문서에서 메인 쪽은 사본이라고 못박는다(erd)

### D-69 옛 기록은 메인에 남기고 러닝 DB는 새 방부터 쌓는다 (2026-11-25)

`공통` · **정함** — migration 「옛 기록」
- **결정** — 분리 전 `running_records` · `running_segments` · `running_splits`는 옮기지 않고 메인에 남긴다. 러닝 세션 서버는 자기 DB(러닝 DB)를 따로 갖고, 분리 뒤 새 방의 기록만 쌓는다. 기록 확인(7-1 · 기록 카드)은 메인이 맡는다. 분리 전 방의 결과(6-1 · 6-2)가 세션 쪽에 필요해지면 그때 옛 데이터를 러닝 DB로 한 번 복사한다.
- **버린 대안** — 논리 복제로 옛 러닝 테이블을 러닝 DB로 옮기기 — 지금 필요 없는 이전 작업과 끊는 시점 조율이 든다
- **이유** — 기록은 바뀌지 않고, 메인 사본이 지금 테이블 그대로다(D-68)
- **확인할 것** — 앱이 결과 대시보드(6-1 · 6-2)를 기록 목록에서 다시 여는 경로가 있는지. 있으면 운영 추출(M7) 전에 옛 방 결과를 러닝 DB로 복사한다 — 6-1 · 6-2는 ALB로 세션에 가고(D-58), 세션은 옛 방을 모른다

### D-70 탈퇴 saga는 메인 오케스트레이션, 정산은 끝내기, 세션 호출 3초 (2026-11-25)

`공통` · **정함** — D-44의 단계를 확정하고 빈칸 둘을 채운다
- **결정** — 러닝 중 탈퇴는 메인이 지휘하는 saga(오케스트레이션)다. `DELETE /users/me` 요청 하나 안에서 메인이 D-44의 단계를 순서대로 진행하고, 지금처럼 성공 또는 503 `ACCOUNT_DELETION_UNAVAILABLE`을 바로 답한다. 세션의 정산은 지금 계약(api-spec 12-4)을 그대로 따른다 — `RUNNING`이면 그때까지 받은 데이터로 끝내기를 확정해 기록이 남고, 시작 뒤 `JOINED`면 강제 종료와 같은 기준의 이탈이다. 메인 → 세션 정산 호출의 시간 제한은 3초이고, 넘기면 기점 전 실패로 보상한다.
- **버린 대안** — 코레오그래피(탈퇴 요청 이벤트 → 세션 정산 이벤트 → 메인 삭제) — 응답이 '접수됨'으로 바뀌어 공개 API가 달라지고, 진행 상태를 아는 곳이 없어 실패 이벤트 · 상태 저장 · 시간 초과 감시를 따로 만들어야 한다 / 정산을 이탈로 줄이기 — 달린 기록이 사라지고 12-4가 바뀐다
- **이유** — 사용자가 결과를 바로 기다리고, 단계가 적고, 실패하면 되돌려야 하는 흐름이다. 지금 탈퇴 코드에 세션 호출 하나를 더하는 크기다. saga는 보상이 필요한 이 흐름에만 쓰고, 러닝 결과 전달처럼 되돌릴 일이 없는 흐름은 아웃박스 · inbox로 맞춘다
- **영향** — [running-session-server/consistency.md](running-session-server/consistency.md) 「계정 탈퇴 saga」 「정하지 않은 것」, [running-session-server/architecture.md](running-session-server/architecture.md) 「동기 호출 허용 목록」, PREREG `K-SC7-*`

### D-71 모집 마감 커밋에 매칭 방을 닫고 러닝 방으로 넘긴다 — 방 확정 이벤트 (2026-11-25)

`공통` · **정함** — D-26의 넘기는 방식을 채운다
- **결정** — 방 주인이 바뀌는 순간은 메인이 방을 `MATCHING`에서 꺼내는 트랜잭션의 커밋이다 — 매칭 방은 시작 10분 전, 초대 방은 1분 전 `CloseMatchingHandler`, 혼자 달리기는 만드는 `OpenSoloRoomHandler`. 메인은 이 트랜잭션에서 매칭 방을 닫고 방 확정 이벤트를 아웃박스에 쓴다. 그 뒤 그 방의 판정(이탈 · 페널티 · 인원 · 방 취소 · 시작 · 끝내기)은 세션만 한다. 세션은 방 확정을 받으면 러닝 세션 · 참가자 · 예약 작업을 '없을 때만 넣기'로 만든다. 세션이 모르는 방에 `RUNNING_START`가 닿을 때만 메인에서 당겨 온다(방 하나에 한 번으로 묶는다). 탈퇴 정산 호출은 방 정보를 함께 싣는다.
- **버린 대안** — 러닝 시작 시각에 넘기기 — 넘기기 여유가 0이라 모든 방의 첫 시작이 메인에 물어보고, 17:59:59 이탈(메인)과 18:00:00 시작(세션)이 다른 DB에서 판정돼 둘 다 성공하는 꼬임이 다시 생긴다 / 이탈 요청이 올 때 마감시키기 — 이탈 하나가 방 전체에 확정 알림을 쏜다
- **이유** — 마감 뒤에는 이탈과 시작을 세션 한 곳에서 같은 참가자 잠금으로 줄 세운다. 넘기기 여유(10분 · 1분)가 CDC 지연을 덮는다
- **같이 넣는 장치** — 방 확정에 모집 마감 시각을 싣는다(페널티 기준이 메인과 같아야 한다) · 마감 트랜잭션이 실패한 방을 다시 돌리는 점검과 'MATCHING인데 마감 시각 + 30초 지남' 알람 · 아웃박스 CHECK 운영 DDL을 코드보다 먼저 · CDC 지연을 시작 5분 전에 감지하면 그 슬롯 방을 미리 당겨 오기 · 세션 방이 남아 있는 동안 메인을 이 버전 아래로 되돌리지 않는다
- **영향** — [running-session-server/architecture.md](running-session-server/architecture.md) 「경계 — 생애 단계」 「넘기기」 「동기 호출 허용 목록」, [running-session-server/runtime.md](running-session-server/runtime.md), PREREG `K-SC14-1`

### D-72 서버 사이 이벤트는 셋 — 방 확정 · 사용자 변경 · 참가자 결과 (2026-11-25)

`공통` · **정함** — D-28을 바꾸고, D-44 4단계의 사용자 삭제 이벤트를 사용자 변경으로 묶는다

### D-73 확정 뒤 대기 · 이탈 · 카운트다운은 러닝 방(세션), 앱이 세션에 직접 — 채팅은 메인 (2026-11-25)

`공통` · **정함** — consistency 「확정 뒤 이탈」을 정한다. D-53의 후보 3(확정 뒤 이탈 전달)과 D-27의 '이탈 응답'을 버린다. 공개 계약을 바꾼다(사용자 요청)
- **결정** — 확정(`MATCH_CONFIRMED`) 뒤 앱은 러닝 WS에 붙어 대기 화면(멤버 변화 · 시작 카운트다운)을 세션에서 받고, 이탈도 세션에 직접 보낸다. 세션이 혼자 판정하고 같은 러닝 방 사람들에게 바로 알린다. 메인은 참가자 결과 이벤트로 몇 초 뒤 알고 자기 것만 고친다. `POST /match-rooms/leave`는 모집 중 방만 받고, 확정된 방이면 409 새 코드로 답해 앱이 세션 쪽으로 다시 보내게 한다. 방 채팅은 메인에 그대로 두고 시작 시각에 닫는다. 나간 사람이 메인 반영 전 몇 초 동안 채팅을 보낼 수 있는 틈은 받아들인다 — 앱은 나가는 즉시 채팅 화면을 닫는다.
- **버린 대안** — 같은 URL로 메인이 받아 세션에 동기로 전달하기 — 앱은 그대로지만 메인이 이탈 경로에 남아 분리가 덜 되고, 메인이 죽으면 확정된 방도 못 나가며, 세션 장애 때 메인이 새 실패를 떠안는다 / 메인이 정하고 세션이 고치기 — 2xx를 받았는데 러닝이 이어지는 경우와 틀린 쿨다운이 생긴다 / 채팅도 세션으로 — 채팅은 러닝 기록이 아니라 메인의 콘텐츠 기능이고 옮기는 일이 크다
- **이유** — 매칭 방은 메인, 러닝 방은 세션이라는 경계가 앱 화면까지 그대로 이어진다. 메인이 멈춰도 확정된 방은 대기 · 이탈 · 시작이 된다(G3)
- **정하지 않음** — 세션이 받는 이탈 요청의 형식(러닝 WS 메시지 vs `POST /running-rooms/{runningRoomId}/leave`), 새 오류 코드 이름, WS 새 메시지 이름 — api-spec을 쓸 때 정한다

### D-81 끝내기에서 잠금 밖은 S3 · 날씨뿐, 계산은 잠금 안 (2026-11-25)

`세션` · **정함** — runtime 「정하지 않은 것」 1(`TrackAnalyzer`를 봉인에 둘지 확정에 둘지)을 정한다. D-63 · D-79의 '분석도 잠금 밖'을 바꾼다 — 잠금 밖 S3 · 날씨 → 짧은 트랜잭션이라는 구조는 그대로다. '분석과 기록 계산은 잠금 안'과 한 번 잠그는 모양은 바뀜 → D-82 (11-25) — 판정(필터 · 목표 판정)은 잠금 안 그대로, 분석은 임대를 쥔 봉인으로

- **이유** — 계산을 잠금 안에서 해야 분석한 트랙과 저장한 기록이 같다. 잠금을 쥔 채 기다리는 외부 호출은 S3 업로드와 날씨다 — run 14에서 남는 원인은 S3 업로드 · 트랙 분석 · 행 잠금 대기이고 날씨는 원인이 아니며, 운영에서는 날씨가 같은 트랜잭션에서 최대 2초 더해진다([load_test/RESULTS.md](../../load_test/RESULTS.md) 「정정 (11-24)」). 분석은 외부 호출이 아닌 계산이라 잠금 안에 둔다

### D-82 끝내기는 판정 → 봉인 → 확정, 겹침은 Redis 임대로 막는다 (2026-11-25)

`세션` · **정함** — D-81의 '분석과 기록 계산은 잠금 안'과 한 번 잠그는 모양을 바꾼다. 목표 판정은 잠금 안(D-80), 잠금을 쥔 채 외부 호출을 기다리지 않는다(D-63)는 그대로다. runtime 「정하지 않은 것」 2(원본 트랙 S3 key)를 정한다
- **결정** — 끝내기를 세 단계로 나눈다. 모놀리스(F1)와 새 엔진 모두 같다.
  1. **판정** (짧은 트랜잭션, 참가자 → 방 잠금) — 이미 끝났으면 ack만 다시. 임대가 있으면 잠금을 놓고 아래 '임대를 본 요청'. 없으면 Redis 트랙을 읽어(스냅숏) `TrackFilter` → 목표 판정. 미달이면 지금처럼 미룬다. 도달이면 임대를 잡고 커밋한다.
  2. **봉인** (잠금 · 트랜잭션 없음, 임대만 쥔다) — 판정의 스냅숏으로 `TrackAnalyzer`. 기록이 남을 때만 S3 원본 업로드 → 날씨 조회(실패하면 기본값).
  3. **확정** (짧은 트랜잭션, 참가자 → 방 잠금) — 이미 끝났는지 다시 확인하고, 끝났으면 저장하지 않고 ack만. 아니면 봉인의 분석으로 기록 · 구간 · 상태 · 페널티 · 평균 페이스 · 방 닫기를 저장하고 커밋한다.
  - **임대** — Redis `SET NX PX`, 값은 요청마다 새 토큰, TTL 30초. 확정 커밋 뒤에도, 봉인 · 확정이 실패해도(finally) 자기 토큰일 때만 지운다(확인 · 삭제를 Lua 한 번에). 프로세스가 죽으면 TTL로 풀린다.
  - **임대를 본 요청은 기다리지 않는다** — 판정은 임대를 한 번만 시도하고, 잠금을 쥔 채 임대를 기다리지 않는다(교착 없음). `RUNNING_FINISH`에는 `ERROR` `RUNNING_TRACK_UNAVAILABLE`(`sourceType: RUNNING_FINISH`)로 답해 재전송을 받는다 — 앱이 이미 '확정되지 않았으니 잠시 뒤 다시 보낸다'로 처리해 앱 수정이 없다. 서버 로그 · 지표는 원인을 따로 단다. 목표 도달 자동 종료(위치 배치)에는 아무것도 보내지 않는다 — 이 경로의 `ERROR`는 로컬 트랙 전체 재전송을 부른다. 다음 배치가 다시 판정한다.
  - **S3 key는 고정 그대로** — `gps-tracks/{userId}/{runningRoomId}/{시작 날짜}.json`. 겹쳐 두 번 올라가면 나중 것(같거나 더 많은 좌표의 원본)이 덮는다.
  - **S3 클라이언트에 전체 호출 시간 제한 10초**(`apiCallTimeout`)를 둔다 — 봉인 시간에 상한을 만들어 TTL 안에 끝나게 한다.
- **버린 대안** — 분석을 확정(잠금 안)에서 하기(D-81) — 분석의 입력(스냅숏 · 고정된 목표 거리 · 설정)은 잠금이 지킬 공유 상태가 아니라 결과가 같고, 잠금 · 커넥션만 분석 시간만큼 더 쥔다 / 봉인을 판정보다 먼저(잠금 하나) — 목표 미달 배치 · 재전송 · 짧은 러닝마다 헛 S3 업로드 · 날씨 조회가 나고, S3 key가 분석 결과에 기대 업로드가 분석을 앞설 수 없다 / 임대를 본 요청이 서버에서 기다리기 — 스레드를 최대 TTL만큼 붙잡는다 / 참가자 상태 `FINISHING` · DB 임대 컬럼 — 운영 SQL · 상태를 읽는 모든 곳 수정 · 갇힌 상태 복구가 든다 / 새 오류 코드 — 앱 출시와 최소 버전 상향이 든다
- **이유** — 잠금 안에는 바뀔 수 있는 상태를 읽고 쓰는 일만 남는다(끝났나 · 목표 판정 · 상태 · 페널티 · 평균 페이스 · 방 닫기). 같은 러너의 봉인은 임대가 한 줄로 세우고, 겹쳐도 확정의 재확인과 `running_records (running_room_id, user_id)` UNIQUE가 기록을 하나로 지킨다. 기다림은 '임대를 쥔 채 DB 잠금' 한 방향뿐이라 교착이 없다
- **대가** — 실제로 끝나는 한 번에 잠금을 두 번 잡는다. 겹친 연결의 재전송은 앞 요청이 끝날 때까지 `RUNNING_TRACK_UNAVAILABLE`을 받는다(재전송 간격은 앱 값). 프로세스가 봉인 중 죽으면 최대 30초 동안 끝낼 수 없다. 이 오류 코드가 저장소 장애와 섞여 원인 태그로 가른다
- **영향** — [running-session-server/runtime.md](running-session-server/runtime.md) 「끝내기」, migration 「선행 수정 F1–F9」, [../api-spec.md](../api-spec.md) 5 `RUNNING_TRACK_UNAVAILABLE`
