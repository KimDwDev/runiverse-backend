# 러닝 세션 서버 — 일관성

메인 서버(running-service)와 러닝 세션 서버가 같은 러닝을 서로 다르게 알 수 있는 곳과, 그것을 어떻게 막고 · 좁히고 · 찾아 · 고치는지 적는다. 불변식, saga가 아닌 것, 확정 뒤 이탈, 러닝 중 계정 탈퇴 saga, 끝낸 뒤 메인이 반영하기 전까지의 창, 대조가 여기 있다. 두 서비스 사이에 상태를 하나 더 두거나 순서를 바꿀 때 여기서 시작한다.

|---|---|
| 경계 · 데이터 주인 · 이벤트 · 동기 호출 | [architecture.md](architecture.md) |

| 지금 탈퇴 코드와 지금 얽힌 곳 | [migration.md](migration.md) 「지금 얽힌 곳 (11-24 기준)」 |
| 검증 시나리오 SC6 · SC7, 무결성 지표 | [verification.md](verification.md) 「핵심 시나리오 SC1–SC7」 「지표」 |

- **불변식 번호는 다시 쓰지 않는다** — 버린 불변식은 줄을 긋고 남긴다.
- **saga 단계는 결정이 먼저다** — 단계 · 기점 · 보상을 바꾸려면 [decisions.md](../decisions.md)에 항목을 쓰고 같은 PR에서 이 문서를 고친다.

## 불변식 I1–I7

깨지면 사용자에게 '잃은 기록'이나 '막힌 신청'으로 보이는 것만 적는다. 확인 칸의 k6 검사는 [verification.md](verification.md) 「지표」, 대조는 「대조」.

| # | 불변식 | 지키는 곳 | 확인 | 상태 |
|---|---|---|---|---|
| I1 | **`RUNNING_FINISHED` ack ⇒ 기록이 남았다** — '메인이 안다'가 아니다. 앱은 ack를 받으면 로컬 트랙을 지운다(api-spec 5-D) | 세션 — 기록 + 참가자 · 방 상태 + 아웃박스 행을 러닝 DB 한 트랜잭션으로 커밋한 뒤 ack ([runtime.md](runtime.md)) | k6 무결성 `ack_without_record` = 0 (SC1 · SC2 · SC3 · SC9) | 정함 (D-24) |
| I2 | **강제 종료 시각(시작 + 6시간, `match.force-finish-offset`) + 10분이 지나 활성인 참가자가 없다** — 혼자 달리기 포함 | 세션 — 강제 종료 · 혼자 달리기 청소기 · 밀린 작업 훑기 ([runtime.md](runtime.md)) | 대조 매일 + 알람 | 제안 (D-29) |
| I3 | **`FINISHED`는 끝 상태다** — 늦은 배치와 ack 뒤 닫힌 연결의 `DISCONNECTED`가 덮지 못한다 | 세션 Redis 화면 상태(`UpdateRunningLocationHandler`의 끝남 검사, `LiveRunningStatus.canChangeFrom`) + 방 · 참가자의 끝 상태 | 대조(끝난 방에 활성 참가자 0) · k6 무결성(끝낸 뒤 보낸 배치가 트랙 · 거리에 없다) | 운영 중 — 분리 뒤 그대로 |
| I4 | **사용자마다 활성 신청은 하나 이하다** | 메인 `running_players`(`deleted_at IS NULL`) — `ExistsActiveApplicationPort` · `ExistsActiveRunningPlayerPort` | 대조 매일 | 운영 중 — 분리 뒤 주인은 제안 (D-27) |
| I5 | **러닝 DB 기록 = 메인 사본 (누락 0)** | 러닝 DB 아웃박스 → Debezium → 메인 inbox, DLT · 건너뜀 알람 | 대조 매일 + SC6 | 정함 (D-24 · D-51) |
| I6 | **자리를 풀기 전에 쿨다운을 건다** | 메인 반영 순서 — 쿨다운 `SET EXAT` 다음에 자리를 푼다 ([architecture.md](architecture.md) 「메인 사본과 반영」) | SC6 · SC7 — 자리가 풀린 뒤 쿨다운 없이 통과한 신청 0 | 제안 |
| I7 | **다음 신청 전에 평균 페이스가 최신이다** | 같은 반영 트랜잭션에서 평균 페이스를 다시 낸 뒤 자리를 푼다 | SC6 | 제안 |

- **I1이 깨지는 길이 하나 남는다** — 커밋은 됐는데 ack가 닿지 않으면(프로세스가 죽음 · 네트워크 · 계획 종료) 다시 붙은 앱의 `RUNNING_START`는 `NOT_ROOM_PLAYER`다(`StartRunningHandler`가 활성 신청만 찾는다). 기록은 남았지만 앱은 로컬 트랙을 지울 신호를 받지 못한다. 지금 코드에도 있는 창이고, 프로세스 경계와 계획 종료가 넓힌다 → 「정하지 않은 것」 5.
- **I2의 강제 종료는 넘기기 때 세션이 건다** — 예약 작업의 주인은 [architecture.md](architecture.md) 「데이터 주인」.

## saga가 아닌 것

`정함 (D-43)` — 이 설계에서 saga는 러닝 중 계정 탈퇴 하나다. 아래는 되돌릴 단계가 없다.

| 흐름 | saga가 아닌 이유 |
|---|---|
| 끝내기 · 목표 도달 자동 종료 | 러닝 DB 로컬 트랜잭션 + 아웃박스, 그 뒤 ack. 메인의 반응은 파생 상태다 |
| 강제 종료 · 노쇼 | 세션 로컬 트랜잭션(러너마다 하나) + 이벤트 |
| 넘기기 | 아웃박스 이벤트 + 멱등 당겨 오기(후보). 늦게 온 이벤트는 아무것도 바꾸지 않는다 — 방식은 정하지 않음 ([architecture.md](architecture.md) 「넘기기」) |
| 혼자 달리기 열기 | 메인 한 트랜잭션(번호 · 신청 · 방) + 넘기기 — 제안 (D-27) |
| 메인 inbox 반응 (사본 · 평균 페이스 · 쿨다운 · 자리) | 세션 결정을 따라 할 뿐이라 되돌릴 일이 없다. 같은 메시지를 다시 받아도 결과가 같다 |
| 결과 조회 6-1 · 6-2 | 세션이 응답한다. 메인 반영 지연은 대조로 본다 (D-58) |
| 기록 카드 | 메인 사본 위의 로컬 트랜잭션 |
| 콤보 보관 | 방 닫힘 커밋 뒤 세션 안의 로컬 단계 |
| 확정 뒤 이탈 | 두 후보 모두 saga가 아니다 — (나)도 정정 이벤트 하나가 더 생길 뿐이다 (「확정 뒤 이탈」) |

**saga를 늘리는 대안은 버렸다**

- **세션이 혼자 달리기 방을 만든다** — 메인 자리에 대한 예약 saga와 고아 예약 청소기가 생긴다 (D-27).

## 확정 뒤 이탈

`정하지 않음` — 넘기기 방식([architecture.md](architecture.md) 「넘기기」)과 함께 정한다. 동기 전달은 [architecture.md](architecture.md) 「동기 호출 허용 목록」의 후보(3)로만 있다 (D-53).

- **겹치는 것** — 명단이 정해진 뒤 `JOINED` 참가자의 `POST /match-rooms/leave`(메인)와 같은 참가자의 `RUNNING_START`(세션)가 서로 다른 DB에서 같은 참가자를 바꾼다. DB를 넘는 잠금은 없다.
- **지금** — `CancelMatchHandler`는 `RUNNING`만 409 `MATCH_ALREADY_STARTED`로 막고, 시작된 방의 `JOINED` 참가자는 나가게 둔다. 두 경로가 같은 DB에서 참가자 → 방 순으로 잠가 줄을 선다.

| | (가) 세션이 혼자 정한다 | (나) 메인이 정하고 세션이 고친다 |
|---|---|---|
| 흐름 | 넘긴 신청이면 메인이 세션에 이탈을 동기로 전한다(허용 목록 3). 세션이 참가자 → 러닝 세션 순으로 잠그고, `RUNNING`이면 409, 아니면 페널티를 판정하고 시작 전이면 방 평균 페이스를 다시 내며 0명이면 방을 취소하고 참가자 이탈 이벤트를 쓴다. 메인은 응답대로 신청을 닫고 쿨다운을 걸고 초대를 `LEFT`로 바꾼다 | 메인이 지금처럼 이탈을 커밋하고 이벤트로 알린다. 세션이 이미 `RUNNING`으로 만든 참가자면 늦은 이탈을 무시하고 정정 이벤트를 보내, 메인이 신청 · 쿨다운을 고친다 |
| 결정자 | 세션 하나 | 메인. 경합하면 세션 |
| 앱에 보이는 것 | 지금과 같은 2xx · 409 | 2xx를 받았는데 러닝이 이어지는 경우가 생긴다 |
| 새 실패 | 세션에 닿지 못하면 상태를 바꾸지 않고 실패한다 — 새 오류 코드가 필요하다 | 없다. 대신 정정 이벤트와 그 반영이 하나 더 생기고, 정정 전까지 틀린 쿨다운이 걸려 있다 |
| 지킬 것 | 호출하는 동안 메인 DB 잠금을 쥐지 않는다 (D-53) | 정정 반영도 멱등이다 |

## 계정 탈퇴 saga

`정함 (D-43)` — 러닝 중 계정 탈퇴가 이 설계의 하나뿐인 saga다. 아래 단계 · 기점 · 보상은 `제안 (D-44)`. 공개 계약(api-spec 12-4)은 그대로이고, 지금 코드(정산을 품은 한 트랜잭션)는 [migration.md](migration.md) 「지금 얽힌 곳 (11-24 기준)」.

메인이 지휘한다.

| # | 누가 | 하는 일 | 실패하면 |
|---|---|---|---|
| 1 | 메인 (트랜잭션) | 사용자를 잠그고 `DELETING`으로 표시한다 — 신청 · 혼자 달리기 · 초대 수락 · 토큰 재발급을 막는다 | 바뀐 것이 없다 |
| 2 | 메인 (로컬) | 넘기기 전 신청이면 메인 상태를 정리한다 — 모집 중 방 나가기 · 방 평균 페이스 · 채팅 · 초대 `LEFT` | 보상: `DELETING`을 풀고 503 |
| 3 | 메인 → 세션 (동기, 허용 목록 2) | 넘긴 신청이면 세션이 정산한다 — **기점**. 멱등 키는 사용자 ID + 탈퇴 ID. 세션은 넘기기 때 받은 몸무게 · 프로필 스냅샷으로 정산해 사용자 행이 필요 없다. 결과는 참가자 완주 · 이탈 이벤트로 메인에 간다 | 기점 전 실패(세션 다운 · 시간 초과 · 트랙을 못 읽음) → 보상: `DELETING`을 풀고 503 `ACCOUNT_DELETION_UNAVAILABLE` |
| 4 | 메인 (트랜잭션) | 삭제한다 — `delete_users` 스냅샷 · 기기 · `users`(CASCADE) · 리프레시 토큰 · access 토큰 차단, 사용자 삭제 이벤트를 아웃박스에 쓴다 | 앞으로 다시 시도한다 — 정산은 되돌리지 않는다 |
| 5 | 세션 (inbox) | 사용자 삭제 이벤트를 받아 프로필 투영에 삭제를 표시하고, 세션 Redis pub/sub으로 모든 세션 인스턴스의 그 사용자 소켓을 닫는다 | inbox 재시도 |

- **기점은 3이다** — 세션이 러닝을 끝낸 뒤에는 되돌리지 않는다. 그래서 1 · 2는 표시만 풀면 되돌아가게 두고, 4는 끝날 때까지 다시 시도한다.
- **503은 보상 응답으로 남는다** — 12-4의 오류 그대로다. D-38(거절만 하기)을 D-43이 바꿨다.
- **5가 다른 인스턴스의 소켓까지 닫는다** — 지금 탈퇴는 같은 인스턴스 소켓만 닫는다(`RunningConnectionCloseListener`).
- **확인** — SC7(탈퇴 saga + 같은 초의 강제 종료), 기준은 [PREREG](../../../load_test/msa/PREREG.md) `K-SC7-*`.

## 종료 뒤 최종 일관 창

`제안 (D-31)` — D-58은 7-1 · 기록 카드가 반영 뒤 보이는 것만 정했다. 나머지 행은 제안이다.

참가자가 끝낸 뒤 메인이 결과 이벤트를 반영하기 전까지, 메인은 그 사용자를 아직 활성으로 본다 — 넘긴 자리를 메인이 혼자 풀지 않기 때문이다 (D-27).

| 보이는 곳 | 반영 전 | 반영 뒤 | 상태 |
|---|---|---|---|
| 매칭 신청 · 혼자 달리기 · 초대 수락 | 409 — 활성 신청이 있을 때와 같은 오류 | 통과 | 제안 (D-31) |
| 친구 초대 대상 | 바쁨 | 초대할 수 있다 | 제안 (D-31) |
| `/users/me/status` (2-2) | `RUNNING`일 수 있다 — 허용 목록 4(활성 확인)가 줄인다. 앱이 이것을 보고 `RUNNING_START`를 보내면 `NOT_ROOM_PLAYER` | `IDLE`, `cooldownUntil` | 제안 (D-31) |
| 평균 페이스 · 쿨다운 | 이전 값 | 최신 (I6 · I7) | 제안 (D-31) |
| 7-1 · 기록 카드 · 홈 활동 · 함께 뛴 사람 | 이 기록이 없다 | 보인다 | 정함 (D-58) |
| 6-1 · 6-2 | 바로 보인다 — 세션이 응답한다 | — | 정함 (D-58) |

- **창의 길이** — 평소에는 CDC 지연만큼이다. Debezium · Kafka가 멈추면 끝이 없다 — 브로커 하나, 복제 1 ([kafka.md](../kafka.md) 「클러스터」).
- **막는 장치** — DLT · 건너뜀 알람 (D-51), 대조 당겨 오기(허용 목록 6, 「대조」), CDC 지연 알람.
- **재는 것** — 다시 신청할 수 있기까지의 시간(`RUNNING_FINISHED` → 신청 통과)과 CDC 지연. 지표는 [verification.md](verification.md) 「지표」, 기준은 [PREREG](../../../load_test/msa/PREREG.md) `K-SC6-*`.
- **버린 대안** — '잠시 뒤 다시 시도하라'는 새 오류 코드 — API 변경이라 승인과 iOS · 안드로이드 최소 버전 상향이 필요하다.

## 대조

`정함 (D-51)` — 결과 이벤트를 받기 전(M2)에 러닝 DB와 메인 사본의 대조를 만든다. 나머지 검사 · 주기 · 알람은 `제안`.

| 검사 | 불변식 | 어느 DB | 어긋나면 |
|---|---|---|---|
| 강제 종료 시각 + 10분이 지나도 활성인 참가자 (매칭 · 초대) | I2 | 지금 서비스 DB → 분리 뒤 러닝 DB | 알람, 강제 종료를 다시 건다 |
| 7시간(`running-track.ttl`)이 지나도 `RUNNING`인 혼자 달리기 | I2 | 같음 | 알람 — 지금은 청소기가 없어 영영 남는다 |
| 끝난 방(`FINISHED` · `CANCELLED`)에 남은 활성 참가자 | I3 | 같음 | 알람 |
| 활성 신청이 둘 이상인 사용자 | I4 | 메인 | 알람 |
| 러닝 DB 기록 중 메인 사본에 없는 것 | I5 | 둘 다 | 대조 당겨 오기(허용 목록 6)로 다시 반영 — inbox와 같은 처리 |
| 넘긴 신청이 강제 종료 시각 + 여유를 지나도 메인에 열려 있음 | I5 · I2 | 메인 | 같은 당겨 오기 |

- **지금 운영에서 먼저 센다** — 분리 전에 I2 · I3 · I4와 7시간 넘은 혼자 달리기 수를 지금 서비스 DB에서 세어 기준선을 안다. 절차는 [RUNBOOK](../../../load_test/msa/RUNBOOK.md) 「0. 운영 증거」, 합계는 [RESULTS](../../../load_test/msa/RESULTS.md) 「0. 운영 증거」.
- **쿼리는 `load_test/msa/sql/`에 둔다** — 검증 회차의 무결성 검사와 같은 쿼리를 쓴다. 매일 도는 운영 작업으로 옮길 자리는 「정하지 않은 것」 6.

## 정하지 않은 것

1. **확정 뒤 이탈** — (가) 세션이 혼자 정한다 vs (나) 메인이 정하고 세션이 고친다(「확정 뒤 이탈」). (가)면 세션에 닿지 못할 때의 오류 코드와 상태값을 정해 도메인별 `*ErrorCode` enum · `GlobalExceptionHandler.toStatus()` · `ErrorExposurePolicy.EXPOSED_CODES`에 함께 넣는다.
2. **정산이 러닝에 하는 일** — 지금 계약(12-4)은 `RUNNING`이면 마지막 수신 데이터로 끝내기, 시작 뒤 `JOINED`면 강제 종료와 같은 기준의 이탈이다. 정산이 이것을 그대로 따를지(강제 종료 경로 — 기록이 남는다), 이탈로 줄일지(기록 없이 끝난다 — 12-4가 바뀐다).
3. **지금 탈퇴 경로와 맞추기** — `DeleteAccountHandler`의 한 트랜잭션을 단계로 나눌 때:
   - PR #116에서 고친 순서 문제(CASCADE가 미뤄진 `LEFT` 갱신보다 먼저 행을 지운다)가 단계 사이에서 다시 생기지 않는지
   - 탈퇴 도중 넘기기(`closeMatching()`)가 겹칠 때 2와 3 중 무엇을 하는지
   - 정산 이벤트가 사용자 삭제 뒤에 메인에 닿을 때 반영이 지워진 사용자를 견디는지(평균 페이스 · 쿨다운 · 초대 행이 없다)
4. **saga 메시지 · 시간 제한 · 멱등 키** — 정산 호출의 경로 · 본문 · 시간 제한(api-spec 14장), 탈퇴 ID를 누가 언제 만드는지, 기점 뒤 4가 실패할 때 앱에 무엇을 답하는지(204를 늦게 줄지, 503 뒤의 다시 시도가 같은 탈퇴로 이어지는지), SC7 통과 기준(PREREG).
5. **커밋됐는데 ack를 받지 못한 앱** — 다시 붙으면 `RUNNING_START`가 `NOT_ROOM_PLAYER`라 로컬 트랙을 지울 신호가 없다. 고치려면(예: 끝난 참가자에게 `RUNNING_FINISHED`를 다시 보낸다) 러닝 WS 계약이 바뀌어 iOS · 안드로이드 최소 버전 상향이 필요하다 — 계약 변경이라 승인 뒤에만 한다.
6. **대조를 매일 돌릴 자리** — 운영 작업을 어디서 돌릴지(EKS CronJob · 앱 안 예약 작업)와 알람이 가는 곳. M2 전에 정한다.
