# 러닝 세션 서버 — 검증

러닝 세션을 나누는 근거([rationale.md](rationale.md))를 하나씩 깨질 수 있게 시험하는 설계다. 비교군, 0단계 운영 증거, k6 시나리오, 플랫폼 검증, k6 밖 확인, 지표 정의, 판정을 적는다. 시험을 더하거나 판정을 바꿀 때 여기서 시작한다.

| 실행 순서 · 장애 주입 · 상태 초기화 | [load_test/msa/RUNBOOK.md](../../../load_test/msa/RUNBOOK.md) |

> 운영 데이터는 집계만 적는다. 주소·키·비밀값은 적지 않는다.

- **얼리기 전까지 덮어쓴다** — PREREG가 이 파일의 커밋 sha를 적는다. 그 뒤 설계를 바꾸면 load_test/msa/RESULTS 「편차」에 남긴다.
- **판정은 「판정과 결과」에만** — 장마다 한 묶음씩 채우고, 같은 PR에서 rationale 「근거 순위」의 판정 칸을 고친다.

## 원칙

`정함 (D-25 · D-45)` — 규칙만 적는다. 숫자는 PREREG 「실행 규칙」 「판정 방식」.

- **근거마다 깨지는 조건이 있다** — 시나리오는 깰 수 있는 근거(G · AG)와 PREREG의 K id를 적는다. 깨는 조건이 없는 시나리오는 돌리지 않는다.
- **러닝 연속성부터 잰다** — 메인 배포 · 장애 중 진행 중 러닝이 이어지는가가 본 질문이다(D-45). 성능 시나리오는 보조다.
- **옛 결과는 기준선만** — load_test/RESULTS.md는 run id로만 인용한다. 10-23 뒤 커밋은 잰 적이 없다.
- **분리 비교군은 A′와만 견준다** (D-34, 제안) — 고치지 않은 A와 B0 · B2를 견준 숫자로 근거를 지지하지 않는다. A vs A′는 따로 낸다.
- **얼리기 전에는 판정하지 않는다** — 기준 · 창 · 판정 규칙 · 비교군별 예측이 PREREG에 커밋된 뒤 첫 회차를 돈다. 회차마다 PREREG sha와 이미지 digest를 남긴다.
- **맞붙는 비교군은 비용이 같다** — 같은 하드웨어, 같은 DB 커넥션 총량, 같은 이미지(역할 · 변형은 env로만). 비용이 다른 것은 대조군이고 순위를 매기지 않는다.
- **부하는 모든 비교군에 같다** — REST는 L30 · L60 · L100으로 얼리고 비교군마다 다시 재지 않는다. 러너 수 · 시드 · 거리 · 페이스는 run_id마다 같다.
- **운영 증거가 먼저다** — 0단계가 G1의 크기를 정한 뒤 SC1을 해석한다.
- **무결성 검사를 못 넘은 회차는 성능 판정에 쓰지 않는다** — 기능 결함으로 따로 적는다(load_test/msa/README 「무결성 검사」).
- **운영에 k6를 대지 않는다** — 운영은 집계(백분위 · 개수 · 시간대 계열)만 준다. 합성 사용자만 쓴다.
- **부하 시험은 전용 환경에서** — dev 머지마다 `docker rm -f`로 갈리는 test EC2를 쓰지 않는다. 앱의 Kafka 컨슈머는 끈다(`KAFKA_CONSUMER_ENABLED=false`) — 부하 시험 인스턴스가 `test` 그룹에 붙어 완료 이벤트를 가져가지 않게 한다([kafka.md](../kafka.md)). 부하 시험 DB에는 지연 탐침 커넥터 말고 Debezium을 붙이지 않는다. Kafka를 멈추는 장애는 버려도 되는 브로커에서만 낸다 — 공유 dev/test 클러스터에서 내지 않는다.

## 0단계 — 운영 증거

`제안 (D-57)` — 운영 권한이 있는 개발자가 뽑는다. 진행 상태는 [README.md](README.md) 「진행 단계」 · 「지금 막힌 것」. 절차 · 쿼리는 RUNBOOK 「0. 운영 증거」(`sql/prod-evidence.sql`), 집계는 load_test/msa/RESULTS 「0. 운영 증거」.

- **정하는 것** — G1의 크기: 운영 배포 때 진행 중이던 러닝 수, 끊긴 연결 수(닫기 코드별), 재연결 수. G1 기각 조건의 운영 쪽 절반(배포 창에 걸린 러닝이 거의 없다)이 여기서 정해진다.

- **배포 목록** — [rationale.md](rationale.md) 「G1 배포 결합」. 다시 뽑는 법은 [deploy-cadence.sh](../../../load_test/msa/scripts/deploy-cadence.sh).

## 핵심 시나리오 SC1–SC7

### SC1 러닝 중 메인 배포 (본 실험)

- **부하** — 400명(방 100 × 4), 10km, 20분 전에 출발한 상태로 좌표 약 1,200개를 미리 채운다. 1초에 좌표 하나, 10초에 배치 하나. 남은 거리는 끊긴 뒤 10–25분 안에 끝나게 맞춘다. REST L60, 앱 SSE 1,000개.
- **주입** — 5분에 운영과 같은 방식으로 배포한다. A′는 계획 종료(F9)를 쓴다. B0-main은 메인 함대만, B2는 메인만 배포한다.
- **본다** — 「지표」의 꼬임 지표 전부, REST 502 · 503 · 504, SSE 재연결, 인스턴스별 WS 연결 수.
- **예측 방향** — A: 바뀌는 인스턴스의 러너가 모두 1006 · 1001로 끊기고 재연결 · 전체 재전송 · 시작 폭주가 한꺼번에 온다. 데이터는 잃지 않는다. A′: 닫기는 4500으로 깨끗해지지만 재연결 수 · 재전송 · 상대 진행 공백은 남는다. B0-main · B2: 러너 끊김 0, 재전송 0, 배치 지연 그대로 — 비용은 SC2로 옮겨 간다.

### SC2 세션 배포 — 분리의 값

- **부하 · 본다** — SC1과 같다. 주입: B0-session은 세션 함대만, B2는 세션만 계획 종료를 켜고 배포한다. EKS에서는 R1이 같은 것을 잰다.

- **깨지는 조건** — 세션 배포 한 번의 끊김 · 재연결 비용이 기준을 넘으면 분리 전에 계획 종료부터 고친다. `K-SC2-*`

- **예측 방향** — A: 장애 동안 인증 REST가 거의 다 실패한다(`BlockedTokenValidator`가 블랙리스트를 대체 없이 Redis에 묻는다). 핸드셰이크도 실패하고, 배치는 `RUNNING_TRACK_UNAVAILABLE` 뒤 재전송으로 회복한다. A′R2 · B2: 세션 Redis가 죽어도 메인 REST는 그대로이고 반대도 같다. 러너는 run 18처럼 재전송 뒤 트랙이 완전하다.
- **깨지는 조건** — G2 기각: A에서 장애 동안 인증 REST 오류가 기준 아래다. A′R2와 B2가 같으면 G2는 저장소를 나눌 근거이지 프로세스를 나눌 근거가 아니다 — 저장소 분리는 D-49로 이미 목표에 있다. `K-SC4-*`

### SC5 슬롯 시작 폭주 + 시작 홉

- **부하** — REST만 5분 → 미리 채운 러너 600명 상시 + SSE 1,000 → T0에 시작 러너 400명(과 1,000명)이 T0 + 0–300ms에 `RUNNING_START`, 방마다 예약된 시작 작업도 T0. 시작과 끝내기를 겹치지 않는다(run 14). 창: 앞 / 폭주 [T0, T0+30초] / 뒤.
- **본다** — 그룹별 REST p95 · 오류, 시작 왕복, 핸드셰이크, 블랙리스트 확인 지연, 예약 작업 늦음, 상시 러너 배치 지연, 시작 시각 전 `RUNNING_START` 거부 비율(유효 조건).
- **예측 방향** — A: run 17처럼 시작 · 핸드셰이크가 느리다(숫자는 PREREG 「비교군별 예측」), 폭주 창에 REST 지연. A′c가 연결 줄 서기를 덜고 A′R2가 더 덜어 낸다. B0는 REST를 세션 JVM에서 뺀다.

### SC6 결과 복제

- **1부 (모든 비교군)** — `RUNNING_FINISHED`마다 바로 6-1을 읽고, 본인이 없으면 30초까지 100ms마다 다시 읽는다. 모놀리스에서 0이 아니면 모놀리스 결함이다. B2에서 6-1은 세션이 응답한다(D-58). B0와 모놀리스 비교군은 메인이 응답한다.
- **2부 (M2 무렵, B2 전)** — 부하 시험 DB에 전용 Debezium 커넥터 · 슬롯과 지연 탐침을 붙여 커밋 → 브로커 → 받음 지연을 끝내기 몰림(SC9 400명 동시 · SC12) 동안 잰다. 10km 결과 한 건(구간 약 1,000행) 크기를 토픽 크기 한도와 견준다. 두 번째 커넥터 · 슬롯 · heartbeat · 알람 연습을 겸하고 끝나면 지운다.
- **3부 (B2)** — 끝내기 몰림 중 회차마다 장애 하나: 브로커 재시작, Connect kill, 깨진 결과 이벤트 하나, 큰 결과 하나, 커넥터 30분 멈춤(WAL 쌓임). 회복 10분 뒤 대조(consistency 「대조」).
- **예측 방향** — 지연 숫자는 PREREG 「비교군별 예측」 B2 SC6. DLT · 알람이 있으면 누락 0.
- **깨지는 조건** — AG5 지지: 어떤 장애 뒤에도 누락이 0이 아니거나 결과가 크기 한도를 넘는다. 기각: DLT와 알람을 둔 채 모든 장애 뒤 누락 0(I5, D-51). AG2는 D-58로 결과 조회가 세션이라, 남는 것은 7-1 · 기록 카드와 다시 신청이 늦는 창의 길이다(D-31). `K-SC6-*`

### SC7 계정 탈퇴 saga + 같은 초 강제 종료

- **부하** — 방 100 × 4. 정한 때 방마다 3명이 끝내지 않고 소켓을 닫는다. 5분 뒤 100방 모두의 `RUNNING_FORCE_FINISH`가 같은 초에 돈다(`match.force-finish-offset` 6시간을 줄인 것). REST L60. 달리는 사용자 10명을 1분에 한 명씩 탈퇴시킨다 — 절반은 소켓이 다른 인스턴스에 있다. 정리할 때 탈퇴시킨 시험 사용자를 되살린다.
- **본다** — 예약 작업 늦음, 강제 종료 끝내기 단계 시간, Hikari 대기, 남은 러너 배치 지연, 탈퇴 지연, 탈퇴한 사용자의 소켓이 모든 인스턴스에서 닫히기까지 걸린 시간(기준 `K-SC7-3`, 정하지 않음).
- **예측 방향** — A: 강제 종료가 방마다 한 트랜잭션이라(`ForceFinishRunningRoomHandler`) 방 하나의 S3 업로드 · 날씨가 한 잠금 아래 돈다. 다른 인스턴스의 소켓은 닫히지 않는다(`RunningConnectionCloseListener`는 자기 인스턴스만). B0: 탈퇴가 메인 함대에서 돌아 세션 함대의 소켓을 하나도 못 닫는다 — 인스턴스를 넘는 닫기 단계가 있어야 한다(AG1 단계 표에 센다). B2: saga 경로(consistency 「계정 탈퇴 saga」). 기점 전 실패를 넣으면 보상(표시 풀기 + 503 `ACCOUNT_DELETION_UNAVAILABLE`).
- **깨지는 조건** — 강제 종료 절(G4): A′(F3)에서 100개 작업이 기준 시간 안에 끝나고 REST · 배치가 기준 안이면 모놀리스 고침으로 충분하다. saga는 I2와 고아 행 0을 본다 — 통과 기준은 정하지 않음([consistency.md](consistency.md) 「정하지 않은 것」). `K-SC7-*`

- **SC14** — 매칭↔러닝 경계 정합성(D-64, B2에서만). 나누면 같은 DB 잠금으로 막던 경합이 서비스 사이로 넘어간다. 세 가지를 잰다 — (1) **넘기기**: 슬롯 하나(방 100개)를 마감해 시작 시각에 세션에 방이 없는 경우와 넘기기 지연. (2) **시작 뒤 나가기 vs 시작**: 같은 참가자의 `POST /match-rooms/leave`와 `RUNNING_START`를 같은 초에 100쌍 보내 결과가 하나로 정해지는지, 메인 사본과 세션 상태가 어긋나는지(대조), 활성 신청이 둘이 되는지. (3) **끝낸 직후 다시 신청**: 400명이 끝내자마자 매칭을 신청해 신청이 받아들여지기까지의 시간, 쿨다운 없이 풀린 자리, 옛 평균 페이스로 들어간 신청. 확정 뒤 나가기의 설계는 정하지 않음이라([consistency.md](consistency.md) 「확정 뒤 이탈」) (2)의 기준은 그 설계를 고른 뒤 얼린다. `K-SC14-*`

## 지표

클라이언트(k6) 쪽 정의만 둔다. 서버 지표 이름은 metrics-convention 「기본 제공과 직접 만드는 것」의 예정 행, 계산하는 곳은 load_test/msa/README 「지표가 계산되는 곳」. 한 방 4명이 한 VU라 상대 진행 · 콤보 · 전파는 한 시계로 잰다.

| 지표 | 정의 | 잡는 꼬임 |
|---|---|---|
| `ws_unexpected_close{code}` | 러너가 열지 않은 닫기 — 끝내기 ack 뒤 닫기와 러너가 연 닫기는 뺀다. 코드별(1006 · 1001 · 1009 · 4001 · 4500 …)로 세고, 배포 · 장애 창 안의 것은 창 태그로 가른다 | 끊김 |
| `reconnect_to_started_ms` | 끊김을 본 때 → 새 연결에서 `RUNNING_STARTED`를 받은 때. 간격 · 재시도 포함. 끝내 못 받으면 `reconnect_success` 실패 | 재연결 |
| `resend_points` | 재연결 뒤 다시 보낸 좌표 수, 첫 묶음 → 마지막 묶음 뒤 내 진행 통지까지 시간(`resend_duration_ms`) | 재전송 |
| `partner_progress_gap_s` | 러너가 받은 상대 하나의 `RUNNING_PROGRESS_UPDATED` 사이 가장 긴 간격, 짝마다. 평소는 배치 주기(10초) 안팎. 기준선은 `running-combo.freshness`(19초) — 넘으면 서버가 그 상대를 콤보 판정에서 관측 없음으로 본다 | 상대가 멈춰 보임 |
| `combo_broken_by_disconnect` | 끊기기 직전 콤보였던 짝 중, 둘 다 일시정지 · 끝내기 없이 재연결 뒤 두 배치 안에 `RUNNING_COMBO_UPDATED`에서 빠진 짝의 비율 | 콤보 끊김 |
| `false_disconnected_broadcast` | 러너가 새 연결에서 `RUNNING_STARTED`를 받은 뒤 상대가 그 러너의 `DISCONNECTED`를 받은 수와, `RUNNING`으로 돌아오기까지 시간 — 다른 인스턴스로 재연결할 때의 늦은 DISCONNECTED(api-spec 5-D가 받아들인 것) | 잘못된 끊김 표시 |
| `track_gap` | 러너가 보낸 sequence 중 S3 원본 트랙에 없는 것 — 빠진 수 · 빠진 시간(`track_gap_s`) · 완전도. 서버 `runiverse.running.location.gaps`(예정)와 맞춰 본다 | 트랙 빈칸 |
| `finish_success` | 끝내기(직접 · 목표 도달 자동)를 처음 보낸 뒤 PREREG가 정한 창 안에 `RUNNING_FINISHED`를 받은 비율, 재시도 포함. 첫 전송 → ack는 `finish_latency_to_ack` | 끝내기 실패 |
| `ack_without_record` | `RUNNING_FINISHED`를 받았는데 회차 끝 SQL에 기록이 없다 — 0이어야 한다(I1). ack 직후 첫 6-1에 본인이 없는 것은 `results_first_get_not_found` | 기록 없는 ack |
| `replication_lag_ms` (B2) | 러닝 DB 끝내기 커밋 → 메인 사본 반영. 함께 ack → 7-1에 보이기까지(`ack_to_main_visible_ms`, 7-1을 폴링) | 늦게 보임 |
| `reapply_wait_ms` (B2) | ack → 같은 사용자의 `/users/me/status`가 `RUNNING`이 아니고 매칭 신청이 `MATCH_ALREADY_IN_PROGRESS` 없이 받아지기까지 — 종료 뒤 최종 일관 창(D-31) | 다시 신청 못 함 |
| `reconcile_missing` (B2) | 회복 10분 뒤 대조: 러닝 DB 기록 − 메인 사본 기록. 함께 중복 반영 · 건너뜀 · DLT 수. 0이어야 한다(I5) | 조용한 유실 |

- **그 밖** — `handshake_status{code}`, 그룹별 REST 지연 · 오류, health 탐침 성공, SSE 재연결, 시작 시각 전 거부 비율, `dropped_iterations`(0이 아니면 회차 무효).
- **콤보와 끊김** — 끊긴 동안 콤보는 붙잡아 둔다([runtime.md](runtime.md)). 꼬임은 `combo_broken_by_disconnect` · `partner_progress_gap_s` · `false_disconnected_broadcast`를 함께 본다 — 어느 길인지 SC1이 가른다.

1. **서버 지표 이름** — WS 연결 게이지(KEDA 신호 겸)를 metrics-convention 「이름」이 잡아 둔 `runiverse.websocket.connections`로 쓸지 `…sessions.active` 꼴의 다른 이름으로 쓸지, `runiverse.websocket.messages`를 예정 행대로 Counter로 둘지 처리 시간을 보려고 Timer로 바꿀지. 정하면 metrics-convention 예정 행과 eks 「엣지 · 자동 확장 · 배포」를 고친다.
2. **k6 원시 결과의 자리** — CSV · 요약 · 무결성 출력을 둘 S3 버킷 · 접두어와 목록(manifest) 모양. 버킷 이름 규칙은 [platform.md](../platform.md) 「S3」.
3. **앱 재접속 값** — 재연결 간격 · 끝내기 재시도 · 재전송 묶음 · `HEALTH_CHECK` 주기 · 1006 처리. SC1 · SC2 · SC3의 클라이언트 모델이 기다린다 — [runtime.md](runtime.md).
