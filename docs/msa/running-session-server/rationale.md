# 러닝 세션 서버 — 왜 나누는가

러닝 세션을 메인 서버(running-service)에서 떼어 내는 이유와, 그 이유를 깨는 조건을 적는다. 출발점은 운영 배포가 진행 중 러닝을 끊은 일이고(D-45), 근거마다 새 k6 시험이 깰 수 있게 짠다(D-25). 근거의 사실에는 날짜와 출처를 달고, 기준 숫자는 적지 않는다.

> 상태: 가설 — 11-24 기준 G · AG 근거는 모두 판정 전이고, X1–X5는 검토하고 버려 `기각`이다. 새 사실은 날짜를 단 행으로 더하고, 있던 행은 고치지 않는다.

## 분리 이유 — 운영에서 확인한 것

정함 (D-45).

- **메인 배포가 진행 중 러닝을 끊는다** — 콘텐츠·러닝 밖 기능을 내는 운영 배포가 모든 인스턴스를 바꾸고, 계획 종료가 없어 그 위의 러닝 WebSocket이 모두 끊긴다(「G1 배포 결합」).
- **앱이라 배포를 밤까지 미룰 수 없다** — 운영 배포 7번 중 5번이 슬롯 시간(18:28–22:38)에 나갔다. 혼자 달리기는 아무 때나 열고 초대 러닝은 23:59까지 시작할 수 있어(feature-spec 초대 러닝) 러닝이 없는 시간대도 없다.
- **매칭은 끊겨도 견디고, 러닝은 꼬인다** — 끊긴 러너는 상대 화면에 `DISCONNECTED`로 보이고, 콤보는 좌표가 다시 올 때까지 멈추며, 다시 붙으면 `RUNNING_START`와 로컬 트랙 전체 재전송을 거친다.
- **그래서 러닝 세션은 안정성을 위해 따로 개발하고, 메인은 콘텐츠와 러닝 밖 기능을 개발한다** — 검증은 메인 배포·장애 중 러닝 연속성을 잰다(SC1–SC7, D-57 제안).
- **성능 때문에 나누지 않는다** — 첫 부하 시험에서 1,000명까지 여유가 있었다(run 13 · 53). 끝내기 폭주(run 14)는 고칠 결함이다(「G4 끝내기 폭주는 고칠 결함」).

## G1 배포 결합

메인 배포마다 진행 중인 러닝 WebSocket이 모두 끊긴다 — 바뀐 코드가 러닝과 무관해도 같다. 나누면 메인 배포는 러닝을 끊지 않고, 끊김은 세션 배포로만 남는다(SC2가 그 대가를 잰다).

## G2 Redis 연결 · 실패 영역 공유

러닝 실시간 상태와 토큰 검사가 Redis 연결 하나와 Redis 한 대를 같이 쓴다. 러닝 쪽 몰림이 인증이 필요한 모든 요청을 늦추고, Redis가 멈추면 러닝과 인증 API가 함께 멈춘다. JVM이 아니라 저장소를 나누라는 근거다 — 목표는 서비스마다 Redis 한 대(D-49, [../platform.md](../platform.md) 「Redis」).

| 날짜 | 사실 | 출처 |
|---|---|---|
| 11-24 | Redis 연결 팩토리를 직접 만들지 않고 풀도 없다 — 자동 구성된 Lettuce 연결 하나를 모두 쓴다(`build.gradle`에 commons-pool2 없음, `spring.data.redis.*`는 주소 · 포트 · 비밀번호만) | 코드 |
| 11-24 | 위치 배치마다 상태를 여러 번 읽고 쓰며 Lua 스크립트를 돈다(`RunningTrackRedisAdapter` · `LiveRunningStatusRedisAdapter`) | 코드 |
| 11-24 | 인증 요청과 WS 핸드셰이크마다 `BlockedTokenValidator` → `AccessTokenRedisAdapter.isBlocked`(`hasKey`)를 거친다. Redis 오류를 대신할 길이 없다 | 코드 |
| 11-24 | 같은 Redis에 채널 `running:room:*` · `match:room:*` · `match:stream:supersede` · `notification:user` · `schedule:job`이 있다 | `*Channel` 클래스 |
| 10-15 | 같은 초 시작에서 위치 배치 꼬리 지연과 핸드셰이크 지연이 함께 늘었다 — 'Redis 연결 하나 + 단일 스레드 Lua'로 봤다(1회 측정) | load_test/RESULTS.md run 17, 「결론」 2 |
| 10월 | Redis를 죽이면 AOF 없이 상태가 조용히 사라졌고(run 16) AOF로 막았다(run 18). 그동안 인증 API는 재지 않았다 | load_test/RESULTS.md run 16 · 18 |

- **깨지는 조건** — A에서 같은 초 시작 폭주 중 REST 지연과 블랙리스트 확인 지연이 기준 안이고, Redis가 멈춘 동안 인증 API 오류가 기준 안이면 깨진다. A′c(연결만 따로)로 풀리면 근거는 '연결 나누기'로, A′R2(Redis 둘)로 풀리면 '저장소 나누기'로 줄어든다 — 어느 쪽도 JVM 분리 근거가 아니다.
- **시나리오** — SC4(A · A′c · A′R2 · B2, Redis마다 장애), SC5(A · A′c · A′R2 · B0, 슬롯 시작 폭주). 기준 `K-SC4-*` · `K-SC5-1`–`K-SC5-4`.
- **판정** — 가설.

## G3 장애 격리

메인 프로세스와 서비스 DB의 장애가 진행 중 러닝을 멈추면 안 된다. 세션이 시작·끝내기에서 메인을 동기로 부르지 않을 때만 선다 — 그래서 결과 조회는 세션이 답하고(D-58) 동기 호출은 허용 목록만 둔다(D-52, [architecture.md](architecture.md) 「동기 호출 허용 목록」).

| 날짜 | 사실 | 출처 |
|---|---|---|
| 11-24 | 위치 배치는 DB를 쓰지 않는다 — `UpdateRunningLocationHandler`에 트랜잭션이 없다 | 코드 |
| 11-24 | 이미 떨어져 있는 것: Kafka · AI 서버(아웃박스 뒤), OAuth(로그인 때만), 토큰(핸드셰이크 때 한 번) | 코드, api-spec 5-C |

| 11-24 | `RUNNING_START`는 DB 잠금을, 끝내기는 DB와 S3를 쓴다. S3 실패는 잡는 곳 없이 끝내기를 실패시킨다(`GpsTrackS3Adapter`) | 코드 |
| 11-24 | health 그룹이 없어 `/actuator/health`가 db · redis를 합쳐 답한다 — 대상 그룹이 이 경로를 보면 DB 순간 장애가 모든 인스턴스를 비정상으로 만든다. 대상 그룹 설정은 저장소에 없다 | `application.properties`, [../platform.md](../platform.md) 「확인할 운영 값」 |
| 10-15 | JVM이 하나다 — 400명 동시 종료 때 앱이 Prometheus 수집에도 답하지 못한 구간이 있었다 | load_test/RESULTS.md run 14 「메모」 |

- **깨지는 조건** — F4(버전 캐시) · F6(health 그룹) · F1(S3를 잠금 밖으로)을 고친 A′에서 서비스 DB 블랙홀 동안 재연결이 거의 다 되고, 회복 뒤 끝내기가 곧 ack되며, 끝나지 못한 러닝이 없으면 모놀리스 안에서 풀린 것이라 분리 근거가 아니다 — 메인 JVM 장애(C7)만 B0 · B2 몫으로 남는다. 설계가 시작·끝내기에 메인 동기 호출을 필요로 해도 깨진다 — 모르는 방 당겨 오기(넘기기-동기)가 그 호출이라 SC5에서 함께 잰다.

## G4 끝내기 폭주는 고칠 결함

한 순간에 몰린 끝내기가 공용 커넥션 풀을 다 써 같은 JVM의 다른 요청까지 막았다. 원인이 고칠 수 있는 코드라 나눠도 같은 `RunningFinisher`가 같은 폭주에서 실패한다. 그래서 옛 엔진에서 먼저 고치고(F1–F9 = A′, D-34 제안) 다시 재며, 분리 근거로는 A′ 뒤에 남는 간섭만 센다.

| 날짜 | 사실 | 출처 |
|---|---|---|

## 받쳐 주는 근거 G5–G8

혼자서는 분리를 설명하지 못하고 위 근거를 받친다.

**G5 배포 주기 차이** — 러닝 경로는 거의 안 바뀌는데 나머지는 계속 바뀐다. 같이 배포하면 메인의 주기와 위험이 러닝에 얹힌다(G1을 받친다).
- 사실 (11-24, `git log --no-merges`, 실시간 경로 67파일 · 3,335줄) — 08-24~09-23 메인 코드 커밋 238개 중 58 · 09-23~10-23 246개 중 48 · 10-23~11-24 432개 중 2(주석 9cd1abf3, 이름 바꾸기 908e3138). 10-23 뒤 운영 배포 5번 중 실시간 경로를 기능으로 바꾼 배포는 없다. 끝내기 경계의 기능 변경은 1건이다 — 6e504e75(초대 방 제재 면제, 11-02 배포) — 매칭 정책이 `RunningFinisher` 안에 있다. 3개월 전체로는 실시간 경로가 줄당 더 자주 바뀌었다 — 만들고 나서 굳은 지 한 달이다.
- 깨지는 조건 — 앞으로 실시간 · 경계 경로가 커밋의 상당 몫을 차지하거나, 운영 배포마다 세션 기능 변경이 따라오면.
- 시나리오 — k6 밖: 배포마다 '세션 배포가 필요했나'를 표시한다(`load_test/msa/scripts/deploy-cadence.sh`).

**G6 연결 확장 단위** — 세션의 용량은 열린 소켓 × 힙이고, 메인은 요청률 × DB 시간이다. 확장 신호가 다르다. 실재하지만 지금 필요하지는 않다.
- 사실 (11-24) — Tomcat 11.0.22가 소켓마다 버퍼를 미리 잡는다(`websocket.max-text-message-buffer-size=64KB` → 소켓당 약 160 KiB, 소스로 계산, 재지 않음). Dockerfile에 `MaxRAMPercentage`가 없어 힙은 기본값이다. 연결 수 게이지가 없어 운영 동시 접속을 모른다. 1,000명일 때 힙은 run 13.
- 깨지는 조건 — J2(`MaxRAMPercentage` 75)가 운영 최대 동시 접속을 크게 넘는 러너를 버티면 지금의 근거가 아니다. 소켓당 힙 기울기가 작으면 원리가 틀렸다.
- 시나리오 — SC11(J1–J4), SC13(보고만). 기준 `K-SC11-*`.

**G7 원시 위치 · 비밀값 가두기** — 1–2초 위치 흐름과 원본 트랙 쓰기는 세션만 필요하다. 나누면 위치와 비밀값을 쥔 배포물이 좁아진다 — 피해 범위의 근거이지 규정 준수의 근거가 아니다.
- 사실 (11-24) — 배포가 Parameter Store 경로 전체를 컨테이너의 `.env` 하나로 내린다(`backend-ci-cd.yml`). JWT는 같은 비밀값으로 HS256 서명 · 검증(`JwtEncoderConfig` · `JwtDecoderConfig`)이라 나눈 세션도 토큰을 만들 수 있다. 메인도 경로 폴리라인을 다룬다(`RouteArtConverter`).
- 깨지는 조건 — 나눈 뒤에도 토큰을 만들거나 원본 위치를 읽는 배포물 수가 줄지 않으면. ES256(D-30 제안)과 버킷 단위 IAM 전에는 오히려 는다. 날씨를 메인이 채우면(D-32 (나)) 시작 좌표가 메인으로 간다.
- 시나리오 — k6 밖: 배포물마다 비밀값 · IAM 권한 · 토큰 발급 가능 여부 목록.

**G8 수집 vs 표시** — '러닝은 수집, 메인은 표시'. 데이터 주인으로는 선다 — 세션은 러닝 사실과 원본, 메인은 사본과 정책(제재 · 쿨다운 · 평균 페이스). 성능 근거로는 깨질 것으로 본다. 경계를 정하는 근거로 쓰지 않는다 — 동사로 나누면 한 애그리거트가 갈린다(D-26).
- 사실 (11-24) — 원본 트랙은 쓰기만 하고 코드에서 읽지 않는다(`GpsTrackS3Adapter`만). 구간 행은 10 m마다(`running-finish.split-distance-meters`) 끝내기 트랜잭션에서 쓰고 6-2만 읽는다(`GetRunningSplitResultsHandler`). 표시 쪽은 `running_records`를 넓게 읽는다 — 7-1이 `record_cards`를 조인하고, 기록 카드가 `running_records`를 잠그고 FK로 묶는다(`RecordCardJpaEntity`). 1분에 퍼진 400명 끝내기는 통과했다(run 15).
- 깨지는 조건 — 끝내기 쓰기 폭주 중 표시 읽기 지연이 기준 안이면 성능 근거로는 깨지고 데이터 주인으로만 남는다.
- 시나리오 — SC12.

## 반대 근거 AG1–AG6

분리가 틀릴 수 있는 이유와 막는 장치다. 확인되면 장치를 고치거나 근거를 줄인다.

**AG1 분산 모놀리스** — 경계가 틀리면 바뀔 때마다 두 서비스를 함께 고치고, 러닝 단계마다 동기 호출이 실패를 옮긴다.
- 사실 (11-24, 조직 저장소 `dev` 첫 부모 머지 자동 집계) — 07-01 뒤 세션 쪽을 건드린 PR의 약 55%, 10-23 뒤 약 80%가 메인 쪽도 건드렸다. 경로 정의에 따라 PR 수가 달라지는 거친 값이라 손 채점 전이다. 지금 코드의 결합은 [migration.md](migration.md) 「지금 얽힌 곳 (11-24 기준)」.
- 확인 — 손 채점한 PR 중 양쪽을 함께 바꿔야 하는 몫이 기준을 넘거나, 러닝 단계(시작 · 재연결 · 끝내기 · 강제 종료 · 시작 뒤 취소 · 러닝 중 탈퇴) 하나라도 메인 동기 호출의 실패로 실패할 때.
- 막는 장치 — 생애 단계 경계(D-26), 더하기만 하는 버전 붙은 계약(D-28 제안), 허용 목록 동기 호출(D-52). 경계를 이렇게 그은 대가로 받아들인다.
- 시나리오 — SC3(B2 · C7), SC7(러닝 중 탈퇴), k6 밖(PR 손 채점, 단계별 동기 호출 목록). 기준 `K-SC3-8` · `K-SC7-3`.

**AG2 비동기 결과** — 앱은 `RUNNING_FINISHED`를 받자마자 결과를 묻는다(api-spec 5-D). 메인 사본으로 답하면 CDC 지연 동안 자기 기록이 없는 결과가 나간다.
- 막는 장치 — 결과 조회 6-1 · 6-2는 세션이 답한다(D-58). 7-1 · 기록 카드는 사본에 반영된 뒤 보인다 — 그 창의 동작은 제안(D-31, [consistency.md](consistency.md) 「종료 뒤 최종 일관 창」).
- 확인 — 세션의 첫 결과 조회가 자기 기록을 못 찾은 경우가 하나라도 있으면.
- 시나리오 — SC6.

**AG3 시작 홉** — 시작·재연결에 원격 호출이 끼면 같은 초 시작 폭주가 더 나빠지고, 메인이 멈춘 동안 시작이 실패한다.
- 사실 (11-24) — `RUNNING_START`는 잠금 둘과 스냅샷(프로필 · presigned URL)을 만든다. 슬롯의 모든 방이 같은 초에 시작한다 — `MatchRoomAssigner`가 `RUNNING_START`를 `startAt`에 걸고, `RUNNING_READY`는 `match.ready-offset`만큼 앞서 나간다. 모놀리스 안에서도 같은 초 시작은 이미 느렸다(run 17).
- 확인 — B2의 시작 지연 · 성공률이 A′보다 기준 넘게 나쁘거나, 메인이 느리거나 멈춘 동안 시작이 실패할 때.
- 막는 장치 — 넘겨받은 방으로 시작하고 모르는 방만 당겨 온다(후보 — [architecture.md](architecture.md) 「넘기기」, 정하지 않음). 18:00 시작 경로에서 메인을 부르지 않는다(D-53 제안).
- 시나리오 — SC5(넘기기-동기 vs 넘기기-사본, B2).

**AG4 운영 부담** — 1~3명 팀에 두 번째 DB · 커넥터 · 복제 슬롯 · WAL 경보 · 배포 파이프라인과 서비스 사이 디버깅이 붙는다.
- 사실 (11-24) — 받칠 것이 아직 없다: IaC 없음(`infra/`에는 filebeat · kafka 설정뿐), 추적 없음(`RequestIdFilter`가 요청마다 새 ID를 만든다), 계획 종료 없음, DLT 없음.
- 확인 — 비용 · 수고 장부와 game-day 두 번(러닝 DB 슬롯이 멈춰 WAL이 쌓임 / 끝내기 몰림 중 브로커 정지)의 탐지 · 복구 시간이나 인프라 비용 증가가 기준을 넘을 때. 기준은 멘토와 정해 PREREG에 둔다.
- 막는 장치 — 예산 절약 배치(D-48), 빌드를 바꾸지 않는 OTel 에이전트(D-55), 결과 전 DLT · 대조(D-51).
- 시나리오 — k6 밖(장부, game-day).

**AG5 Kafka 조용한 유실** — 결과 이벤트가 사라지면 메인 사본에서 그 기록이 영영 빠진다 — 7-1 · 기록 카드에 안 보이고, 메인이 자리를 혼자 풀지 않으므로(D-27 제안) 그 사용자의 활성 상태도 남는다.
- 사실 (11-24) — 노드 한 대 · 복제 계수 1 · 파티션 1([../kafka.md](../kafka.md) 「노드가 하나라서」). inbox는 처리할 수 없는 메시지를 ERROR 로그만 남기고 건너뛴다(D-12, [../outbox-inbox.md](../outbox-inbox.md) 「처리할 수 없는 메시지」).
- 확인 — 브로커 재시작 · Connect 정지 · 깨진 이벤트 · 큰 결과 뒤 대조에서 누락이 하나라도 있으면.
- 막는 장치 — 결과 이벤트를 받기 전(M2)에 DLT · 건너뜀 알람 · 대조(D-51, [consistency.md](consistency.md) 「대조」). 구간 기록은 이벤트에 싣지 않는다(D-28 제안).
- 시나리오 — SC6.

**AG6 같은 jar 두 함대** — 모놀리스 안 수정(F1–F9) + 실시간 상태 전용 Redis + 계획 종료 + 같은 jar를 두 함대로 돌리면 분리 없이 G1–G4가 풀릴 수 있다.
- 사실 (11-24) — 인스턴스 사이 전달이 이미 Redis pub/sub이라 WS만 받는 함대가 지금 코드로 돈다(레이어 규칙 ([docs/architecture.md](../../architecture.md)) 「다중 인스턴스」). 나누는 선은 ALB 경로 규칙(러닝 WS · 6-1 · 6-2 → 세션 함대, [architecture.md](architecture.md) 「공개 경로」)이고, WS 함대의 예약 작업 · Kafka 컨슈머는 역할 플래그로 끈다(B0 — [verification.md](verification.md) 「비교군」).
- 확인 — 근거마다 B0가 그 근거의 기준을 채우면 그 근거는 함대 나누기 몫이다. 모두 채우면 러닝 DB · CDC를 둘 이유는 데이터 주인(G8)만 남는다.
- 막는 장치 — 없다. 대조군이다 — B0는 목표 모양이 아니다.
- 시나리오 — SC1(B0-main) · SC3 · SC5 · SC9 · SC11의 B0 칸, SC4는 A′R2(PREREG 「판정 방식」 AG6). 기준 `K-SC1-4` · `K-SC3-3` · `K-SC4-3` · `K-SC5-4` · `K-SC9-4` · `K-SC11-5`.
